## 场景已确定：家用（患者居家自助）

这一条改变了后续所有细节，先记在最前面：

- **使用现场没有治疗师**。患者在自己家里、用自己的手机做训练。
- **一台设备基本等于一个人**。不存在"治疗室一台平板轮流给 5 个患者用"的情况。
- **网络不可控**。家庭 WiFi 不稳、老人手机会被系统杀后台。
- **没人会点"确认上报"**。每局弹一次同意，等于让数据永远传不上来。

因此：**设备级 token 的方案作废**（那是多人大屏的思路），改为微信登录 + 患者账号；**手动上报作废**，改为静默自动 + 离线补传。详见文末「九、家用场景的架构修订」。

## 一句话结论

**技术栈不用换，数据模型要改。**

`server/` 作为一个"记录接收器"是合格的：鉴权、幂等、校验、413、优雅退出都做了。但它现在收上来的记录**没有主语** —— 服务端无法回答"这条记录是哪个患者的"。所以下一步不是选框架、不是上数据库，而是**先给数据模型补上身份维度**，否则接再多数据也做不出任何一份康复报告，将来还得洗数据。

正确的顺序是：

| 阶段 | 做什么 | 为什么在这个位置 |
| --- | --- | --- |
| P0 | 微信登录 + 患者档案 + `patientId` + 参数快照 + 自动上报 | 家用没有治疗师在场，这五样缺一样数据就进不来 |
| P1 | 配置下发（治疗师改一次，患者下次进游戏生效） | 产品体验最痛的点，且改动极小 |
| P2 | 治疗师看板 + 疗程处方 + 依从性提醒 | 家用的价值在"远程看得见"，不在单机游戏 |
| P3 | JSON → SQLite → Postgres，报表与审计 | 数据到量了再换，换的时候只改 store |

## 二、三个结构性缺口

### 缺口 1：记录没有患者主语（最严重）

一条上传到服务端的记录长这样：

```json
{ "recordId": "rhythm_1759..._a1b2", "gameId": "rhythm",
  "nickname": "体验用户", "score": 2496, "rhythmAccuracy": 0.62 }
```

`nickname` 是用户在「我的」页自己填的，可以随时改、可以重名、可以留空（默认"体验用户"）。

后果：

- 治疗师问"李大爷这周稳定率有没有进步"，**答不出来**。要么全表按 nickname 模糊匹配（会串号），要么重做一遍数据采集。
- 100 个居家患者的记录全混在同一个 `records.json` 里，服务端只知道"有个昵称叫体验用户的传了一条"，不知道对应哪个档案。**家用场景患者越多，这个问题越致命**。
- 隐私合规要求"用户可删除本人数据"，现在删不掉 —— 分不清哪条是他的。

**注意**：这不是"再加个字段"那么简单。`nickname` 是**显示名**，不是**主键**。需要引入 `patientId`（建议用机构内编号，如 `P-0231`，而不是真实姓名），`nickname` 退化成可改的标签。

### 缺口 2：单令牌 = 所有人共用一把钥匙

`UPLOAD_TOKEN` 是全局唯一令牌，靠人工填在设置页里。

后果：

- 令牌泄露只能**全网轮换**，所有设备重填。
- 服务端无法区分"这条数据是谁传的"，出事查不到来源。
- 令牌是长驻的静态字符串，没有过期、没有刷新。

家居场景下这条路彻底走不通：**不可能让七十岁的患者去设置页里粘贴一串 48 位随机字符**。

正确做法是微信登录 —— `openid` 就是天然的身份，永久稳定，换手机也不丢（见 9.2）。原来的 `UPLOAD_TOKEN` 应该被 JWT 取代，而不是被"设备 token"取代。

> 补充说明：如果将来做"治疗室大屏共用"的版本，那时才需要设备级 token（`device` 表 + 可吊销）。家用版不需要，别提前建这张表。

### 缺口 3：配置只在本地，无法下发

现在治疗师要给 5 个游戏分别改参数。患者的手机在家里，治疗师根本碰不到。

这和你的产品目标（"难度、命中区域、发射频率由治疗师实时调整"）是直接矛盾的 —— 原来调整的是**这一台设备**，而家用场景需要调整的是**这个患者**，且要远程生效。

而且这里藏着一个更隐蔽的问题：**记录里没有完整的参数快照**。

现有记录里有零散几个字段（`difficulty`、`holdToleranceDeg`），但不全。一旦治疗师把容差从 6° 改成 4°，历史记录的 `holdRate` 就**不可比了** —— 同样的 62%，在 6° 容差下是"勉强达标"，在 4° 容差下是"表现不错"。没有快照，这份数据在康复评估上就是废的。

## 三、目标数据模型

核心原则：**记录必须自带解释自己的上下文**。

```
organization  机构（单机构时省略，org_id 用常量 'default'）
  └─ therapist   治疗师 —— 微信登录，role = 'therapist'
       └─ care_link  绑定关系（多对多，支持转诊/换人）
  └─ patient     患者 —— 微信登录，role = 'patient'（编号 + 化名，不存真实姓名）
       ├─ plan     疗程处方（本周做哪几个游戏、什么难度、几次）
       ├─ config   按游戏分参数（可下发，带 version）
       └─ record   训练记录（带 patient_id + config_snapshot）
```

一次完整的居家链路：

```
治疗师门诊建档（可选）→ 患者回家微信登录 → 自动生成患者档案，进入待认领池
  → 治疗师看板点一下「认领」→ 下发计划与参数
  → 在家训练 → 静默自动上报（失败进队列）
  → 治疗师看板看到趋势与异常
```

### 表设计

家用场景下核心变成三组：**账号与绑定**（谁是患者、归哪个治疗师）、**参数**（治疗师下发）、**记录**（带快照上报）。

完整可执行的建表语句在 **`server/schema.sql`**（SQLite 方言，含索引、视图、迁移到 Postgres 的说明）。这里只列关键结构：

```sql
-- 账号：患者和治疗师同一张表，role 区分。openid 是身份根
CREATE TABLE app_user (
  id           TEXT PRIMARY KEY,
  openid       TEXT NOT NULL UNIQUE,       -- ★ 微信身份，换手机不丢
  role         TEXT NOT NULL,              -- 'patient' | 'therapist'
  display_name TEXT NOT NULL,              -- 患者用化名
  org_id       TEXT,                       -- 单机构时用常量
  birth_year   INTEGER,                    -- 只存年份
  created_at   INTEGER NOT NULL,
  disabled_at  INTEGER
);

-- 绑定：患者 ↔ 治疗师，多对多（转诊、会诊不丢历史）
CREATE TABLE care_link (
  patient_id   TEXT NOT NULL,
  therapist_id TEXT NOT NULL,
  status       TEXT NOT NULL DEFAULT 'active',   -- active | revoked
  linked_at    INTEGER NOT NULL,
  PRIMARY KEY (patient_id, therapist_id, status)
);

-- 参数：可下发，version 单调递增供客户端增量拉取
CREATE TABLE game_config (
  patient_id  TEXT NOT NULL,
  game_id     TEXT NOT NULL,
  version     INTEGER NOT NULL DEFAULT 1,
  payload     TEXT NOT NULL,               -- 键与 ConfigStore 的 SCHEMA 同名
  updated_by  TEXT, updated_at INTEGER NOT NULL,
  PRIMARY KEY (patient_id, game_id)
);

-- 记录
CREATE TABLE record (
  id            TEXT PRIMARY KEY,          -- 客户端 recordId，天然幂等
  patient_id    TEXT NOT NULL,             -- ★ 核心：主语
  game_id       TEXT NOT NULL,
  started_at    INTEGER NOT NULL,          -- 训练开始（客户端时钟，允许迟到上报）
  duration_sec  REAL NOT NULL,
  score         INTEGER,                   -- 抽成列，便于聚合排序
  accuracy      REAL,
  metrics       TEXT NOT NULL,             -- 游戏特有指标 JSON
  config_snapshot TEXT NOT NULL,           -- ★ 本次完整参数 + version
  data_source   TEXT NOT NULL,             -- 'sensor' | 'simulation'
  interrupted   INTEGER DEFAULT 0,
  created_at    INTEGER NOT NULL,          -- 服务端时间
  deleted_at    INTEGER,
  UNIQUE(id)
);
CREATE INDEX idx_record_patient_time ON record(patient_id, started_at DESC);
CREATE INDEX idx_record_game ON record(game_id, started_at DESC);
```

三个设计取舍要说清楚：

1. **`metrics` 用 JSON，但 `score` / `accuracy` / `duration_sec` 抽成列**。
   5 个游戏的指标差异很大（接水果有 `holdRate`，节奏有 `rhythmAccuracy`，走钢丝有 `stableSec`），全建表要 5 张；全塞 JSON 又没法索引和排序。混合模型：**要聚合/排序的抽列，游戏特有的进 JSON**。将来加第 6 个游戏不用改表。

2. **`config_snapshot` 是必须的，不是可选的**。
   它的作用不是"存档"，是**让历史数据可比较**。报表页要能显示"本次容差 ±6°，稳定率 62%（同容差下较上次 +8%）"。

3. **`data_source` 必须留，并且统计默认排除 `simulation`**。
   现有客户端已经标了这个字段（`training-record.js:102`），服务端现在只是当普通字段存着。**演示数据混进康复报告是最容易出的医疗事故**，必须在查询层默认过滤。

### 鉴权：P0 就上 JWT，不要中间态

```json
POST /api/v1/auth/login   { "code": "wx.login 拿到的 code" }
→ 200 { "token": "<JWT>", "expiresIn": 7200, "role": "patient", "bound": true }

JWT payload:
{ "uid": "u_xxx", "role": "patient", "orgId": "default", "exp": 1759... }
```

- 有效期 2 小时，小程序 `onLaunch` 静默重登（`code` 换新 token），用户无感
- 服务端用 `SESSION_SECRET` 签名（HS256），密钥进环境变量，不进代码
- `code2session` 需要 `APPID` + `SECRET`，只放服务端环境变量

**删掉 `UPLOAD_TOKEN` 这条路**。原来那套"令牌填在设置页"在治疗室场景能忍，家用场景不可能让老人去填 48 位随机串。

### 配置下发的具体接法（改动很小）

现有 `utils/config-store.js` 已经提供了 `patch(partial)` 和 `getStore()`，它天生就是为"外部注入参数"设计的：

```js
// 新增 utils/remote-config.js（约 60 行）
// 1. 读本地缓存的 version
// 2. GET /api/v1/config/:gameId?patientId=&since=version
// 3. 有变更 → store.patch(payload)   ← 复用现有校验/coerce/persist 全链路
// 4. 写回新 version
```

关键点：**服务端下发的必须是和 `SCHEMA` 同名的键**，这样 `patch()` 会自动做类型转换、范围裁剪、步长对齐（`config-store.js:97`）。服务端不需要实现第二套校验逻辑，只管存和发；校验仍由客户端的 `validate()` 兜底。这样治疗师就算从后台塞了一个越界值，也不会把游戏搞崩。

## 五、技术选型：三条路，用规则选而不是拍脑袋

| 方案 | 备案 | 运维 | 数据可迁移 | 复杂查询 | 适合 |
| --- | --- | --- | --- | --- | --- |
| 微信云开发 CloudBase | **免**（用微信域名） | 零 | 差（导出受限） | 弱 | 只想快速上线、不碰服务器 |
| 自建 Node + SQLite | **要** | 低（单文件备份） | **好** | **强**（真 SQL） | 现在这个阶段 |
| 自建 Node + Postgres | **要** | 中（备份/升级/连接池） | **好** | **强** | 多机构、多实例 |
| CloudBase Run（云托管） | 免 | 零 | 中 | 看你连什么库 | 想跑自己的 Node 又不想运维 |

### 这个项目的路线其实已经定了

结合 `server/deploy/WINDOWS.md` 的既有结论：**VDI 只有内网，只做开发/联调；生产走那台 Ubuntu 服务器**。

既然生产机已经有了，"要不要用微信云开发"这一层不用再纠结 —— 云开发的价值是"免服务器免运维"，而你已经有机器、有 nginx、有 PM2。走云开发反而要把 `wx.request` 改成 `wx.cloud.callFunction`，是纯负担。

所以技术栈锁定为：**自建 Node**。

剩下的选择只有一个：`store.js` 后面接什么（JSON / SQLite / Postgres）。这个已经通过 SSH 实测定下来了 —— 见文末「十、服务器实测与最终架构」。

**注意**：之前文档里写的"用 Docker 部署"不成立，那台机器上没装 Docker，装它反而会多占 200~300MB 内存，并且和宝塔的 iptables 规则容易打架。实际用 PM2。

### 如果将来情况变化，判断规则

1. **已经拿到备案域名了吗？**
   - 拿到了 → 自建 Node，把 `store.js` 换成 SQLite（见下）。
   - 没拿到，且 2 个月内要交付给临床 → 走微信云开发，先用 `wx.cloud.callFunction` 顶上，`training-record.js` 只需换掉 `wx.request` 那一处（第 197 行）。
   - 没拿到，但只是内部演示 → 继续局域网 `http://192.168.x.x:8787`，不加"不校验合法域名"就上不了真机。

2. **要对接医院 HIS / 电子病历吗？**
   - 要 → 必须自建 + Postgres，云开发的数据在微信体系里，对接会非常难受。
   - 不要 → SQLite 可以撑很久。

3. **会不会多机构？**
   - 会 → Postgres（需要 `org_id` 隔离 + 行级权限）。
   - 不会（就一个机构）→ SQLite 完全够，几万条无压力。

### 为什么推荐 SQLite 而不是直接上 Postgres

- 你现在是**几个游戏、每天几十条**的量级。上 Postgres 意味着：装服务、配连接池、写备份脚本、处理版本升级 —— 全是运维成本，换不来任何收益。
- SQLite 是**真 SQL**：`GROUP BY patient_id, week` 这种周报查询直接写，比 `store.js` 里手写 `filter` 强太多。
- **备份就是拷一个文件**（比 `records.json` 还简单，且 WAL 模式下不会读到半个写）。
- 迁移路径清楚：SQL 语法 90% 通用，`store.js` 的 `add/list/stats` 三个方法签名不变，换驱动即可。
- 服务器上的 Node 24 **原生支持 `node:sqlite`，不需要任何启动标志**（已实测，见第十章），**依然零依赖**，和你现在的设计哲学一致。
- 你服务器的实际余量：1.7GB 内存已用 52.9%，Postgres 空跑就要 100~150MB，会让这台机器开始吃 swap。

### 不要做的事（这个阶段的过度设计）

- ❌ 微服务拆分 —— 一个服务都还没跑满
- ❌ Redis —— 没有需要缓存的量
- ❌ WebSocket 实时推送配置 —— 小程序进页面时拉一次就够，用 version 号判断
- ❌ 自建账号密码 —— 用微信登录
- ❌ K8s —— 一台 2 核 1.7G 的机器都用不满
- ❌ **装 Docker** —— 这台机器没有 Docker，装了 dockerd + containerd 要多占 200~300MB，且和宝塔的 iptables 规则容易打架。已有 PM2，直接用它
- ❌ **邀请码 / 扫码绑定** —— 居家老人输码失败率太高，改成"待认领池 + 治疗师点一下"
- ❌ **ORM（Prisma / Drizzle）** —— 10 张表 + 聚合报表，ORM 只会多一层要同步维护的 schema，裸 SQL 更快更清楚
- ❌ **用 Node 转发静态图片** —— nginx 直接托管文件，性能高一个量级；Node 只处理 API
- ❌ 一开始就设计多租户权限矩阵 —— 先 `org_id` 占位，等真有第二个机构再说

## 七、合规与安全（康复数据是敏感个人信息）

训练记录包含姿态、稳定性、平衡能力 —— 在国内属于**医疗健康类敏感个人信息**，适用《个人信息保护法》的单独同意要求，不是普通用户数据。

必须做到的：

- **单独同意**：现有 `consent: true` 机制是对的（`training-record.js:173`），但要写清楚"传到哪台服务器、谁能看到、保存多久"。现在弹窗只列了字段，没列这些。
- **最小化**：不存真实姓名、身份证、手机号。患者用编号 + 化名。`birth_year` 而不是生日。
- **可删除**：软删 + 定期物理清理，且要有删除入口。现在 `pages/mine/mine.js:75` 写着"数据均保存在本机"，接后端后这句文案必须改，否则是虚假陈述。
- **审计**：谁改了谁的参数，必须留痕（P3 的 `audit` 表）。
- **传输**：必须 HTTPS，微信小程序强制。
- **不要往第三方分析 SDK 里塞训练数据**。

如果将来对接医院，可能涉及等保二级，那时再评估，现在不用提前做。

## 九、家用场景的架构修订

家用把"治疗师在场"这个隐性假设抽掉了，五个地方要改。

### 9.1 上报：从"每次确认"改为"一次授权 + 静默自动"

现在 `training-record.js:173` 要求每次上传都传 `consent: true`，界面上就是一局弹一次窗。

治疗室里治疗师会点，家里没人会点。结果就是：**做了一周训练，一条数据都没传上来**。

改法：

```
首次登录 → 一次性的隐私授权页（列明字段/用途/接收方/保存期限）→ 用户勾选
之后每一局 → 静默上报，不再询问
"我的"页保留总开关 → 关掉后只存本地，不再上传（且明确告知）
```

隐私弹窗的内容要重写 —— 现在 `describeFruit()` 这类函数只列"发什么字段"，还需要列"发给谁、谁能看、存多久、怎么删"。

### 9.2 身份：设备 token 作废，改微信登录

一台设备一个人的前提下，设备 token 是多余的一层。而且它有个家用场景的硬伤：**老人换手机，记录就断了**。

`wx.login` → `code2session` → 服务端拿 `openid` → 签发自有 JWT：

```
JWT payload: { uid, role: 'patient'|'therapist', orgId, exp: 2h }
刷新：小程序启动时静默重登（code 换新 token），用户无感
```

`openid` 是身份根，永久稳定。换手机、换微信都不影响（除非换微信号，那属于换人）。

**不要**把 openid 直接当 token 用 —— 它是永久标识，泄露即永久泄露。

### 9.3 绑定：待认领池 + 治疗师认领（无邀请码）

**不要邀请码。** 让七十岁的人输 6 位码，失败率比想象中高得多：读错 O/0、过期、输一半退出、家里没人帮忙。

改成"患者登录即进池子，治疗师点一下认领"：

```
【治疗师门诊建档（可选，推荐）】
  治疗师建 patient：编号 P-0231、化名张*爷、出生年、患侧/禁忌
  → user_id 为空（"纸质档案阶段"）

【患者回家首次打开小程序】
  → 微信登录
  → 系统自动建 patient（user_id = 自己，display_name = 微信昵称）
  → 直接能练：本地记录 + 云端记录都正常写，数据不会丢
  → 此刻这条档案进入「待认领池」

【治疗师认领】
  看板 → 待认领池：张** · 10-28 22:31 首次登录 · 已登录 1 台设备
  → 点「认领」：
     · 若门诊已建档 → 把这条挂到 P-0231 上，记录一并迁移
     · 若没建档   → 直接认领，补填档案信息
  → 建立 care_link，下发训练计划与参数
```

三个关键点：

1. **未认领的患者也能正常训练、正常上传。** 不能因为"还没人认领"就不让练 —— 那会把依从性直接杀掉。数据挂在临时档案上，认领时 `UPDATE record SET patient_id=...` 迁移过去即可。
2. **档案与账号分离**（`patient` 表独立于 `app_user`）。治疗师建档时患者还没登录，如果用一张表就会出现"必须先登录才能建档"的倒挂。
3. **认领错了能撤回**（`care_link.status='revoked'`），患者端会显示"已绑定：王治疗师"，绑错了患者自己也能发现。

`care_link` 做成**多对多**：转诊、会诊、换治疗师都不丢历史。这是居家康复的常见情况，一开始做成一对一会很痛。

> 待认领池就是一个视图 `v_unclaimed_patient`（见 `server/schema.sql`），不用额外表，也不用定时清理。

### 9.4 网络：离线优先是硬需求，不是优化项

家庭网络 + 老人手机的组合，上传失败是常态而不是异常。

现有设计其实是对的骨架 —— 本地先存、`recordId` 幂等、失败记 `retry`。缺的是**自动化**：

- 训练结束 → 自动触发上传（不等用户点）
- 失败 → 指数退避重试（1s / 5s / 30s），超过 3 次不放弃，标记为待补传
- `onLaunch` / `onShow` / 网络恢复 → 扫一遍 `uploadState in (local, failed)` 的记录批量补传
- 服务端 `/records` 支持一次 20 条批量（`index.js:150` 已有），补传直接复用

服务端要能接受**迟到很久**的记录：一条 3 天前离线产生的记录，`startedAt` 是 3 天前，`receivedAt` 是现在。现有实现已经区分这两个时间，没问题。

> 补传时不要去重到"丢数据"：`recordId` 冲突返回 200 算成功，客户端把状态改成 `uploaded`。

### 9.5 治疗师：从"操作设备"变成"看数据"

这是家用模式真正的产品形态转变。

治疗师不再碰患者的手机，他需要一个看板：

| 视图 | 内容 |
| --- | --- |
| 患者列表 | 姓名/化名、上次训练时间、本周完成 x/y 次、**异常标记** |
| 单人趋势 | 按周聚合：训练次数、时长、得分、稳定率；**同参数归一化**后再比 |
| 参数调整 | 直接改该患者的 `game_config`，version+1，患者下次进游戏生效 |
| 异常预警 | 连续 3 天未训练 / 稳定率较上周跌 > 20% / 数据中断率高 |

异常预警是居家场景最有价值的功能 —— 治疗师不可能每天翻一遍所有患者，需要系统把人推到眼前。

**注意"同参数归一化"**：跨周对比必须先看 `configSnapshot` 是否一致。容差从 6° 改到 4°，稳定率的绝对值不能直接比。这是 `config_snapshot` 字段存在的真正理由。

### 9.6 依从性：居家康复的第一指标

临床数据很一致：居家康复的失败原因主要是**不练**，不是练得不对。

所以后端从一开始就要留这些位：

- `care_plan` 记录"本周该练几次"
- 视图 `v_patient_week` 算"实际练了几次"（见 schema.sql）
- 订阅消息提醒：到点没练 → 推送（需要用户每次授权一次性订阅，或申请长期订阅）

订阅消息的坑要提前知道：微信的**一次性订阅**发一条用一次，用户不点就废；**长期订阅**需要对应类目资质。家用场景建议先做"一次性订阅 + 在训练结束时顺手埋下一次授权"，把授权攒起来。

### 9.7 家用最大的技术风险不在后端

必须说清楚：**风险在蓝牙**。

WT9011DCL 是 BLE 设备，小程序 BLE 在 iOS / Android / 各家 ROM 上表现差异很大。老人手机（内存小、省电策略激进、蓝牙栈老旧）是重灾区。

后端能做的是**别把脏数据当真实数据**：

- `dataSource` 必须严格区分 `sensor` / `simulation`，统计默认只算 `sensor`
- `interrupted` / `interrupted_sec` 必须真实记录（现有 `rhythm` 已经有）
- 单局中断率过高时，这条记录在报告里要标灰，而不是参与均值

否则治疗师看到的"稳定率下降"可能是蓝牙掉的，不是患者退步了 —— 这是会导致错误临床判断的问题。

### 9.8 家用特有的边界情况

| 情况 | 处理 |
| --- | --- |
| 老人不会用微信 / 没有微信号 | 子女用自己微信登录，代管父母档案。需要 `app_user` 支持"一个 openid 管多个 patient"，schema 里已留 `care_link` 可扩展，暂不做 |
| 患者同时被两个治疗师看（转诊） | `care_link` 多对多，天然支持 |
| 患者换手机 | openid 不变，重新登录即恢复，历史全在云端 |
| 患者要求删数据 | 软删 + 30 天后物理删；同时通知关联治疗师 |
| 患者自行改难度 | 患者端不给改游戏参数，只能改音量/振动这类偏好；参数由治疗师控制 |

最后一条容易忽略但很重要：**患者不能改治疗参数**，否则"处方"就失效了。现在的 `ConfigStore` 是全开放的，接入下发后要按 `role` 区分可写字段。

```
└── logs/             pm2 日志
```

> 数据目录放在 `/www/wwwroot` 下会被 nginx 当静态文件直接暴露 —— 这是最常见的数据库泄露方式。用 `/opt` 干净。

### 10.4 部署形态

PM2，`fork` 模式，**单实例**：

```js
// ecosystem.config.js
module.exports = {
  apps: [{
    name: 'rehab-api',
    script: 'server/index.js',
    instances: 1,              // ★ SQLite 必须单实例，cluster 多进程会写冲突
    exec_mode: 'fork',
    max_memory_restart: '200M',
    env: {
      NODE_ENV: 'production',
      PORT: 8787,
      DATA_DIR: '/opt/rehab/data',
      SESSION_SECRET: '（openssl rand -hex 32）',
      WX_APPID: '（小程序 AppID）',
      WX_SECRET: '（小程序 AppSecret，只放这里）'
    }
  }]
}
```

`instances: 1` 不是保守，是**必须**：SQLite 的 WAL 支持并发读，但写仍然串行。开 cluster 会在高并发写入时拿到 `SQLITE_BUSY`。

nginx 反代（宝塔 → 网站 → 设置 → 配置文件，加一段）：

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8787;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 30s;
}
location = /health {
    proxy_pass http://127.0.0.1:8787/health;
    access_log off;
}
client_max_body_size 1m;
```

只反代 `/api/` 和 `/health`，不要把 `/` 整个转发过去 —— 否则将来任何路径处理失误都会直接暴露。

### 10.5 唯一的阻塞项：没有域名

实测 nginx 里**一个域名都没配**，443 也没服务，`/www/server/panel/vhost/cert` 目录都不存在。

这意味着一件事：**小程序真机现在上不了线**。

微信的规则是硬性的：`wx.request` 的合法域名必须是 **HTTPS + 已备案**，不接受 IP、不接受 http、不接受未备案域名。

| 阶段 | 能不能跑 | 怎么做 |
| --- | --- | --- |
| 开发者工具模拟器 | 能 | 勾「不校验合法域名」，直连 `http://127.0.0.1:8787` |
| 真机调试（开发版） | 能 | 手机端打开调试模式，同样勾不校验，用 `http://47.112.18.198:8787` |
| 体验版 / 正式版 | **不能** | 必须 HTTPS + 备案域名 |

所以：

1. **今天就该去买域名并提交备案。** 这是纯行政时间（2~3 周），你写代码再快也压缩不了它。80 端口已经能从公网访问，说明阿里云安全组是通的，备案下来后配证书只要十分钟。
2. 备案期间照常开发：服务先起在 8787，用真机调试模式联调。
3. 域名下来后：宝塔里申请免费证书 → 加 vhost → 微信后台填 `request 合法域名`。

> 如果已经有别的域名（哪怕指向别处），加一条子域解析到 47.112.18.198 也可以，但**子域同样要在备案范围内**。

### 10.6 备份与运维

SQLite 的好处在这里体现得最明显：

```bash
# 在线备份（不会锁表，不会读到半个写）
sqlite3 /opt/rehab/data/rehab.db ".backup '/opt/rehab/backup/rehab-$(date +%F).db'"

# 或者直接拷（WAL 模式下要先 checkpoint）
sqlite3 /opt/rehab/data/rehab.db "PRAGMA wal_checkpoint(TRUNCATE);"
```

建议加一条 cron，每天凌晨跑一次，保留 14 天：

```bash
0 3 * * * sqlite3 /opt/rehab/data/rehab.db ".backup '/opt/rehab/backup/rehab-$(date +\%F).db'" && find /opt/rehab/backup -name 'rehab-*.db' -mtime +14 -delete
```

如果以后数据重要到不能只放本机，再把 `.backup` 产物 `rclone` 到对象存储。**现在不用**，多一个依赖多一个故障点。

### 10.7 这台机器上的风险清单

| 风险 | 现状 | 建议 |
| --- | --- | --- |
| 单机无冗余 | 挂了服务就停，没有备用节点 | 居家康复可接受；等有付费用户再考虑 |
| 内存已用 52.9% | 宝塔 + 阿里云组件占 600MB 固定开销 | 新服务控制在 100MB 以内；加功能前先看 `free -m` |
