# FR-GAME-01 · 射击训练（体感静态保持 · 战机打外星人）

微信小程序原生 Canvas 2D 实现的康复射击游戏。患者佩戴 WitMotion WT9011DCL 传感器，
通过**身体左右移动**驾驶战机，把机头对准悬停在前方的**外星人**持续射击。按实机佩戴方向，
左右移动读取传感器的 **Pitch 轴**（实测该轴对应左右方向），Roll 仅缓存；战机按**镜像方向**跟随患者。
**保持在范围内才会自动开火**；偏离超过 `keepRangeDeg` 立即停火（清空在飞子弹）、暂停每秒基础分，
外星人露出**眯眼得意**（停火嘲笑）；被击中时露出**`>_<` 皱眉表情**。
治疗师可在训练过程中实时调整判定范围、发射频率、难度、得分区间与保持范围，**无需重启游戏**。
战机与外星人都是矢量绘制（见第 8 节），只有激光与粒子用 Kenney CC0 贴图，贴图加载失败时同样回退矢量。

## 3. 核心逻辑

### 3.1 双时钟（engine.update）

```
帧循环 canvas.requestAnimationFrame  →  update(dt)  →  render()
   ├── 0.1s 累加器  accTick：score.onTick(tickIndex, hitBucket)
   │      累计击中次数、连击判定、连击奖励结算
   └── 1.0s 累加器  accSec ：score.onSecond(inZone)
          游戏总时长推进（elapsedMs 累加 → 60s 倒计时）、基础分累加
```

命中判定在**渲染帧内做线段扫掠**（`HitDetector.sweep`），命中先入 `hitBucket`，
等 0.1s 刻度到点再统一结算——既防穿透又满足「0.1s 累计击中」口径。
右上角显示**整数秒倒计时**（`Math.ceil(timeLeft)`），60 → 59 → … → 0 后结算。

### 3.2 连击算法（score.js）

```
combo = (tick - lastHitTick) <= comboWindowTicks ? combo + 1 : 1
base  = randomInt(scoreMin, scoreMax)
mul   = min(1 + (combo - 1) * comboStep, comboMaxMul)
gain  = round(base × 难度系数 × mul)
```

### 3.3 传感器 → 左右（pose.js）

```
实机佩戴方向：左右移动读 Pitch 轴（实测对应左右方向），Roll 仅缓存
  → 角色镜像：angle = -pitch（只影响角色屏幕位置）
  → 身体方向：bodyAngle = pitch（HUD 倾角 / 回中提示）
  → 一阶低通 smooth（默认跟手度 0.6，按 dt 换算，最低按 0.5 处理）
  → 中心死区 deadzoneDeg
  → norm = clamp(angle / maxLeanDeg, -1, 1)  →  x01 = (norm+1)/2
  → inZone = |bodyAngle| <= keepRangeDeg
```

- `maxLeanDeg` 从 30° 收紧到 20°（更灵敏）；`keepRangeDeg` 从 18° 收紧到 6°，
  符合康复「静态保持」的容错要求，小角度偏离即触发反馈；
- **采样频率固定 60Hz**：`engine.js` 的 `SENSOR_HZ = 60`，姿态按 `1000/60 ms` 固定步长消费，
  与渲染帧率解耦（渲染掉帧时一次补多步、高刷屏每帧仍更新，平滑手感一致）；
- **硬件输出频率**：连接成功后自动 `WitBle.setOutputRate(100)`，写 JY/WT 协议寄存器 `0x03`
  （模块只支持 0.2/0.5/1/2/5/10/20/50/100/200Hz 离散档位，**没有 60Hz 档**，取 100Hz 保证 ≥60Hz 数据）；
  状态条会显示实测收包帧率（`sensorHz`），可据此确认链路是否达标。设置失败不影响使用；
- 蓝牙传感器页（`pages/wit`）的 Roll / Pitch / Yaw 与原始值统一保留 **2 位小数**
  （`toFixed(2)`，传感器分辨率约 0.0055°）；标定页的实时姿态同步为 2 位小数；
- **已取消**「左右移动轴」与「左右反向」开关：左右移动固定读 Pitch，角色位置做固定镜像；
  但 `bodyAngle` 始终保留患者身体的真实方向，HUD 倾角与「身体偏左/右」回中提示都用它，
  不会因为角色镜像而把提示方向带反；
- 1.2s 无新帧判定掉线 → 自动切到触屏模拟（左右拖动画面）。

### 3.4 保持范围与固定怪兽

怪兽固定于屏幕水平中央（`cx`）、垂直 `0.40H` 处，轻微上下浮动，不移动、不消失。
患者把准星（角色）保持在中间即可持续命中：

| 事件 | 效果 |
| --- | --- |
| 出界（`|bodyAngle| > keepRangeDeg`） | **立即停火**并清空在飞子弹、每秒基础分暂停、外星人**眯眼得意**（带轻微弹跳）、红框 + 「请向右偏 / 请向左偏」提示 + 震动、`miss.mp3` |
| 回到范围 | 恢复自动开火与基础分、`back` 事件、外星人恢复平静 |
| 击中 | 得分 + 飘字 + 粒子 + 连击判定，外星人 **`>_<` 受击表情**（闭眼 + 张嘴）约 0.7s |

> **回中提示按屏幕里的小人给方向**（`charDir`，取镜像后的 `pose.norm`）：
> 小人偏左 → 「请向右偏 →」，小人偏右 → 「← 请向左偏」，小人居中但身体越界 → 「请回到中间」。
> HUD 的「倾角」仍显示患者身体真实角度（`bodyAngle`），两者用途不同。

## 4. 治疗师 / 管理员实时调整 API

模块门面 `utils/game/index.js`，页面内 `require` 使用，也已挂到全局：
`getApp().globalData.gameApi`（控制台 / 其它页面 / 远程指令可直接调用）。

```js
const game = require('/utils/game/index.js')

game.setHitArea(80)          // 击中判定半径（px），运行中立即生效
game.setFireRate(6)          // 发射频率（发/秒）
game.setDifficulty('hard')   // 难度档位，同时套用预设参数
game.setScoreRange(2, 6)     // 得分浮动区间
game.setKeepRange(4)         // 保持范围 ±°
game.setMaxLean(18)          // 满量程倾角（越小越灵敏）
game.setComboWindow(600)     // 连击窗口(ms)
game.patch({ baseScorePerSecond: 2 })

game.getConfig() / resetConfig() / getState()
game.start() / pause() / resume() / restart()
```

实现方式：setter 只写 ConfigStore 并广播，`GameEngine` 每帧/每次判定现读配置，
所以全部参数都是热生效；改 `hitRange` 还会自动闪出判定虚线圈 1.4s。

## 7. 已知限制

1. Canvas 在 Skyline 渲染器下无法在开发者工具中调试（微信已知限制），本页使用页面级
   `renderer: webview`（同 `pages/calibrate`）。
2. 触屏模拟只在传感器掉线时生效，真机连接后以传感器为准。
3. `audio/game` 素材来自公开示例仓库，商用请替换（见 `audio/game/CREDITS.md`）。
4. 贴图在 `assets/games/shoot/`（Kenney CC0，约 10KB）；加载走 `canvas.createImage → base64 → 矢量兜底`
   三级降级，任何一级失败都不会白屏。替换素材保持文件名不变即可，比例变了要同步改 `_drawMonster()`。
5. 左右方向固定按实机 Pitch + 镜像处理（`utils/game/pose.js` 的 `MIRROR_SIGN`），
   运行时不再提供反向开关；若整套佩戴方向相反，把该常量从 `-1` 改为 `1` 即可。
6. 硬件没有 60Hz 档位，只能设 100Hz；若模块拒绝写寄存器，实际仍是默认 10Hz（手感会靠平滑补偿），
   可看状态条的实测 Hz 判断。

## 8. 2.5D 纵深改造（2026-10-29）

### 背景：赛车「看起来像 3D」其实是纯 Canvas 2D

赛车那张图一行 WebGL 都没有，靠四件事叠出来的：

| 手段 | 赛车实现 | 代码量 |
|---|---|---|
| 相机投影 | `Se()` 把 `world.{x,y,z}` 投到屏幕 | 8 行 |
| 近大远小 | 景物尺寸 = `screen.w`（与 z 成反比） | 1 处乘法 |
| 空气透视 | `1 / e^(u²·4.2)`，u = 深度/视距 | 1 行 |
| 地平线同帧 | `compute()` 只算投影、`paint()` 才落笔 | 拆两个方法 |

射击原本已有同一套透视公式（`y = horizonY + floorH / u`，见 `scene2d.js`），
缺的不是技术，是**坐标不统一**：地面是画上去的背景，物体只有屏幕 (x, y)，
两者不在同一个空间里，所以读起来像「一块 UI 盖在图上」。

### 改了什么

| 项 | 位置 | 说明 |
|---|---|---|
| 地面发光通道 | `scene2d.drawFloorPath()`（新增） | 梯形从「脚下 = 判定边界」直连消失点，linearGradient 向远端渐隐到 0 |
| 网格提对比 | `scene2d.drawGround()` | 竖直放射线 alpha 0.085→0.16，三条地平带 0.05/0.08/0.12 → 0.07/0.11/0.17 |
| 背景视差 | `engine._drawBackground()` | `sc.parallax` 由 `playerX` 推出，星 ×0.35 / 行星 ×0.6 / 山脊 ×1.0 |
| 子弹纵深 | `bullet.js` + `engine._drawBullets()` | 出膛 `k=1` → 目标处 `k≈0.45`，同时透明度轻微衰减 |
| 山脊超扫 | `scene2d.drawRidge()` | 横向多画 ±32px，否则视差平移后边缘露缝 |

### 三条不能动的红线

1. **`keepHalfPx()` 是判定边界**。光柱左右边界必须严格等于它，`tools/scene2d-test.js`
   第 3 节钉着。所以**光柱本身不做透视收窄**——患者看到的范围必须就是判定范围。
   纵深交给它脚下的地面通道去做（通道近端宽度 = 2×half，远端收到 16%）。
2. **视差只作用于装饰层**。地面、光柱、怪兽、子弹一律不平移。光柱一动，
   患者看到的范围和实际判定就对不上。
3. **子弹缩放纯粹是视觉**。`HitDetector` 只用目标半径与 `hitRange`，**根本不读
   `bullet.r`**。测试里专门断言 `bullet.r` 保持 3.4 不变，防止后人误以为缩过。

### 子弹纵深的实现

```js
// bullet.js：构造时给出参考面（枪口 y → 怪兽 y）
setDepthRange(nearY, farY)   // 由 engine._layout() 每帧同步
// 进度以「这颗子弹的出膛点」为起点，不是全局枪口：
// 打空后子弹继续往上飞，t 锁在 1，不再继续缩小（否则缩成一个点，像消失了）
let t = clamp01((b.oy - b.y) / (b.oy - farY))
b.k = 1 - 0.55 * t
b.a = 1 - 0.22 * t
```

`k` 只进绘制：`h = 36*k`、`lineWidth = 3.2*k`、尾迹长度也乘 `k`
（只缩端点不缩尾迹，看起来像一根固定的棍子）。参考面没设时 `k` 退化为有限正数，
不会出 NaN——测试第 3c 节守着。

### 已知不做的

- **弯道 / 坡度**：患者要站定保持姿势，视野晃动是干扰项，不是沉浸感。
- **真 3D**：2026-10-29 上过一次 three.js 全量 3D，真机调通前整体回滚。
  原因（WebGL 上下文只能 getContext 一次、tree-shaking 对 three 无效、
  官方 miniprogram 版没有 GLTFLoader）在 `MEMORY.md` 里记全了，别再重走。
- 怪兽现在位于地平线**以上**（`MONSTER_Y_RATIO`），视觉上是「浮在空中」。
  改它会改变判定几何，属于玩法改动，不在本次画面改造范围内。

### 测试

`tools/scene2d-test.js` 61 → **77 项**。三节钉住纵深相关的红线：

- `[3b] 地面通道接地边界 = 判定宽度` —— 通道近端必须严格等于 `2*half`，
  和光柱同一条红线。
- `[3c] 子弹纵深` —— 单调不增、终值 0.45±0.01、透明度不淡到看不见、`bullet.r` 不变。
- `[3d] 背景视差平移后不露缝` —— 四种屏宽下断言山脊左右都超扫 ≥ 2% 屏宽且不过量。

## 9. 主题改版：战机打外星人（2026-10-29）

### 为什么改

原版是「站在光柱里的小人打绿色萌系小怪兽」。两个问题：

1. **视角矛盾**：玩家飞船用的是 Kenney 的**俯视**侧滚射击贴图，却摆在透视地面上。
   俯视的机翼和地面透视永远不是同一个相机，画面读起来像「贴纸盖在背景上」。
2. **形象不对**：主题要的是「战机打外星人」，萌系怪兽（小圆眼 + 微笑嘴）读不出外星感。

### 换成什么

| 元素 | 原 | 新 | 位置 |
|---|---|---|---|
| 玩家 | Kenney 俯视飞船贴图 + 矢量小人兜底 | **后视战机**（矢量）：掠翼机身 + 座舱盖 + 翼尖航行灯 + 双引擎光团 + 机炮口焰 | `_drawPlayer()` / `_shipBox()` |

### 三个关键判断

**1. 后视角度下尾焰是「光团」，不是「锥体」**
第一版按侧视经验画了两根朝下的长锥，结果在屏幕上读成两颗白牙。后视/追尾视角里尾焰是
朝镜头喷的，看到的是光团。改成径向渐变的圆形光斑 + 一小团白心。

**2. 剪影必须用「窄峰」而不是「平滑起伏」**
原来两层 sinusoid 叠出来的山脊，无论怎么调参数都会被读成「地球上的远山」，一眼把太空
题材拉回地面。改成垂直窄峰 + 平顶塔楼之后才读得出异星城市。尖塔用 `hash01(i, salt)`
生成，**同一宽度下重建结果恒定**，不会因为 resize 而换一副天际线。

**3. 双眼必须留中缝**
外星人第一版 `ex = 0.42hw`、`ew = 0.36hw`，两只眼内缘只差 `0.12hw`，糊成「一副墨镜」，
外星感全没了。现在是 `ex = 0.44hw`、`ew = 0.31hw`，中缝 `0.26hw`，才分得开。

### 表情三态（沿用原来的语义，只换画法）

| 状态 | 触发 | 画法 |
|---|---|---|
| 平静 | 正常训练 | 实心杏仁眼 + 高光点 + 细微笑线 |
| 眯眼得意 | 患者出界、停火 | 眼睛纵向压到 `0.22`（一条缝）+ 一边嘴角上挑 + 轻微弹跳 |
| 受击皱眉 | 刚被命中（`sad > 0`） | 向内指的 `><` 折线 + 张嘴 + 全头白闪（峰值 alpha 0.32） |

受击眼睛**不能用 `∩` 弧**：弧线一律被读成「笑眼」，打中了反而像在开心。

### 素材清理

`ship.png` 与 5 张怪兽贴图已从 `assets/games/shoot/` 删除，`sprites.js` 的 `ASSETS`
只剩 `laser.png` / `star.png`。回退方法见该目录 `CREDITS.md`。

### 顺手修掉的预览工具问题（很关键）

`tools/shoot-preview` 有两个一直存在、但没人发现的问题：

1. **贴图从来没在预览里加载过**。`sprites.js` 的 `BASE` 是 `/assets/games/shoot/`，
   这是「代码包根目录」的绝对路径；浏览器里会被解析成 `file:///assets/...` → 404，
   于是整屏一直退回矢量兜底。**之前所有预览截图都不是真机画面**（画的是一个矢量小人）。
   修法：`sprites.js` 增加 `setBase()`，预览启动时改成相对路径。
2. **`engine.stopLoop()` 是空操作**，引擎的方法名是 `_stopLoop`。所以预览里循环从没停过，
   冻结那一帧会被内部循环覆盖 —— 截出来的图和以为的那一帧不是同一帧。
   修法：`freezeEngine()` 直接调 `_stopLoop()`。

同时给预览加了两个观察参数（只影响截图，不影响引擎）：

- `?zoom=N&zx=&zy=` 把指定点放大到窗口中心，用来检查小尺寸元素的细节；
- `?face=normal|smug|hit` 定格表情，否则自动开火下几乎只能截到受击画面。

## 11. 三次改版：靶子换成机械哨兵（2026-10-29）

### 为什么不再做「生物」

患者对上一版大眼外星人的反馈是「太恐怖」。那次已经把恐怖特征逐条拆干净了
（眼白、钝下颌、圆头、腮红、柔光），但**问题不在细节，在类型**——「一张脸」这个
形式本身就在邀请人去读表情，而康复场景不需要患者去解读威胁。

换成**机械造型**之后这类问题一次消失：没有眼球、没有表情、不会被读成「有意图」。
同时机械零件天生适合做动态——旋转、摆动、扫描、脉动都是它的正常状态，
不像生物那样一动就要有情绪。

### 结构

| 部件 | 动态 | 作用 |
|---|---|---|
| 装甲躯干（六边形） | 无（硬边对称，保持识别稳定） | 主体轮廓 |
| 中央能量核心 | 三层环以不同角速度**反向旋转** + 内核 `sin(t*5.2)` 脉动 | 最强的「在运转」信号 |
| 顶部传感器 | 横向扫描缝，亮点以 `sin(t*1.25)` 左右扫视 | 读成「在搜索」，而不是「在看你」 |
| 双机械臂 | 液压式摆动 `sin(t*1.7) ± 0.11rad` | 悬浮姿态感 |
| 双推进器 | 光团 `sin(t*4.4)` 脉动 | 悬浮感的来源 |
| 浮游炮 ×2 | 水平椭圆轨道 `t*1.15` 绕飞，**分前后两趟画** | 整幅画面里动态最强的一处 |
| 扫描光带 | `t*0.42` 自上而下扫过机体（quality≥2） | 细碎的「活着」感 |

警戒态（患者出界）：核心与传感器转琥珀红、浮游炮转速 ×1.8、机械臂摆幅加大。
受击态：装甲过曝 + 六条火花从核心向外溅。

### 一条红线：绘制中心必须严格等于判定中心

这是本次最重要的改动，也是一个**既有 bug 的修复**。

上一版写的是 `const y = m.y + Math.sin(this.t * 2.2) * 3 * s` —— 靶子整体随呼吸上下浮
±3px，而靶子半径只有 22px（`targetRadius` 默认值）。**视觉中心与判定中心最多差 14%**，
患者瞄的位置和子弹判定的位置对不上。这和「光柱边界必须等于 `keepHalfPx()`」是同一条
医疗红线，只是之前没人注意到靶子这边也有同样的偏移。

所以本次所有动态都放在**零件和环绕物**上，整体不平移、不缩放、不抖动：

- 悬浮感交给**阴影**（`scene.softShadow` 随呼吸伸缩）和**推进器脉动**，不靠挪本体；
- 受击反馈用**装甲过曝 + 火花**，而不是常见的「整体抖三下」——抖动同样会瞬时偏移中心；
- 浮游炮绕飞时圆心始终是判定中心，飞到哪里都不影响瞄准。

### 两个画出来才发现的问题

1. **左机械臂画到身体内侧去了**。`rotate(sx * a)` 之后仍沿本地 `+x` 画，`sx=-1` 时
   就指向了右方。正解是先 `scale(sx, 1)` 翻转本地 x 轴再 `rotate(a)`。
2. **传感器整条刷成一块白砖**。`fillRect` 铺满渐变 + `lighter` 混合，读成「方框」而不是
   「扫描缝」。改成暗底 + 只在扫视位置做径向亮斑。

另外：底部原本是六边形的尖角，读成「一面盾牌」；加了外凸的悬浮推进舱之后才像一台机体。
推进舱格栅必须细而淡，三条粗线会读成「牙齿」，反而把机械拉回生物感。

### 测试

`tools/shoot-ui-test.js` 第 9 节（13 项）重写，从「审美断言」改成「行为断言」：

- 源码级：靶心必须直接取 `m.x / m.y`，不许出现 `const y = m.y + …`；
- 源码级：本体内至少三处 `Math.sin(this.t…)`，核心必须是三层反向环；
- **真跑两帧**（用能记录全部绘制调用的 trace ctx）：
  - 同一 `t` 两次绘制**完全一致** —— 动效来自时钟，不掺随机；
  - 不同 `t` 绘制**必须不同** —— 否则「动态感」只是说法；
  - 受击帧绘制数必须多于常态（过曝 + 火花真的画了）。

射击界面测试保持 66 项。

## 12. 四次改版：靶子换成城市光核（2026-10-29 深夜）

前三版改的都是**造型**（外星人 → 去恐怖化 → 机械哨兵），这一版改的是**语义**。

### 12.1 先算清楚靶子在这个游戏里到底是什么

三条数据放在一起，结论就变了：

| | 数值 | 含义 |
| --- | --- | --- |
| 靶子 x | 恒等于 `cx`（`_resetMonster` 里写死） | 它从不移动 |
| 子弹 | 垂直向上（`spreadDeg` 默认 0） | 命中条件 = `\|playerX - cx\| <= hitRange` |
| 保持区半宽 | 55.5px（`keepRangeDeg` 6° / `maxLeanDeg` 20°） | 在光柱内几乎必中（标准难度 `hitRange` = 60） |

也就是说：**「瞄准」是假的**。患者不需要瞄准任何东西，他只需要保持身体位置。
靶子的真实职责是**告诉患者「我现在做得对不对」** —— 它是一个状态指示灯，不是一个攻击目标。

另一组数字同样值得记下来：`targetRadius` = 22（看到的），`hitRange` = 60（判定的）。
**患者看到的靶子只有判定范围的 1/2.7，而 `showHitArea` 默认关闭。**
这意味着他不知道自己打到多偏算中 —— 而光柱那边一直严守「看到 = 判定」的红线，
靶子是唯一没守的地方。这是遗留问题，见 12.5。

### 12.2 为什么机械哨兵是错的

不是因为不好看，是四条语义错误：

1. **五个游戏里只有射击是「攻击」**。接水果是收集、走钢丝是平衡、节奏是接音符、
   赛车是竞速。同一个患者上午接水果、下午消灭敌方哨兵，气质不兼容。
2. **出界时敌人「得意」**（`m.smug`，原文档写「眯眼得意·停火嘲笑」）。
   用羞耻驱动患者，对运动功能障碍的人是挫败。而且这是居家自助训练，没人接住这个情绪。
3. **它全身都在动**（浮游炮绕轨 / 机械臂液压摆动 / 核心三层环反向旋转 / 传感器扫视 /
   扫描光带），而它的职责是当**视线锚点**。每一样动态都在把视线从中心带走。
   上一版的测试甚至专门断言「零件必须真的在动」—— 那是钉错了方向。
4. **它是画面里最暗的东西**（金属灰蓝 `#0B1524 → #2A405F`），比光柱暗、比引擎暗、
   比 HUD 暗。作为视觉焦点，它靠「形状复杂」抢注意力，不是靠「亮」。

### 12.3 现在的设计：点亮一座城

**靶子 = 城市上空的一颗能量光核；命中 = 点亮城里一盏灯；出界 = 灯逐盏熄灭。**

为什么是这个：

- **训练动词是「维持」，不是「消灭」**。静态保持训练的本质就是维持，
  而「充能 / 点亮」正是维持的视觉化。词对了，感觉才对。
- **频率问题**：60 秒 × 3 发/秒 = 180 发，靶子要挨一百多次。
  任何「生命体」被打一百次都荒谬；但「一百次命中点亮一百盏灯」是天然的节奏。
  同一个参数（3 发/秒）从缺陷变成了优点。
- **惩罚是「失去」而不是「被惩罚」**。患者看到的是「我的城在暗下去」，
  不是「它在笑我」。同样的强度，但不羞辱人。
- **成果可见**。结算页第一行不是总分，是「点亮 60 / 75 盏灯火」。
  对这一局来说，一座亮起来的城比 1280 分有意义。
- **叙事闭环**。光柱从地面升起 → 汇聚到光核 → 你在光柱里维持供能 → 城市亮着。
  光柱第一次有了存在的理由，不再是「一块没有出处的发光板」。

### 12.4 实现要点

**数据（`scene2d.buildScene`）**
- `lamps`：塔身上的窗灯，**按离屏幕中心的水平距离升序排好** —— 光从中间向两侧长，
  不是随机亮。窗数按塔高定（`h*w/4.5`，1~13 扇），间距恒定才像人一扇扇开的。
- `street`：街道灯带，`ny = 0.0015 + rand^1.7 * 0.028`，幂次 1.7 让绝大部分挤在底部。
  **这层不逐个点亮**，整体亮度直接跟 `light` —— 它负责「整座城在变亮」，
  `lamps` 负责「又亮了一盏」。
- 只有 `street` 是不够的（读成一条横线），只有 `lamps` 也不够（几十个 1px 点撑不起一座城）。

**绘制（`scene2d.drawCityLights`）**
- 三层：地平线暖色辉光（`0.60 * light^1.25`，`scale(1, 0.135)` 压扁）→ 窗灯逐盏 →
  街道灯带整体。
- 必须画在 `drawGround` **之后**：辉光要盖在地面网格上才像「城市的光映在地上」，
  画在前面会被地面的近处压暗层吃掉。
- 跟着剪影一起做视差（`translate(parallax)`），否则灯会从塔身上滑下来。

**回路（`engine.js`）**
- `LIGHT_PER_HIT = 0.007`（全中约 48 秒铺满，留余量给中途出界）
- `LIGHT_DECAY = 0.035`/秒（出界 3 秒掉 10.5%，约 15 发补回来）
- 命中在 `_collide` 里加，衰减在 `update` 里减，都只在 `STATE.RUNNING` 时生效。

**光核（`_drawBeacon`，替换掉 `_drawSentry` / `_drawSentryBody` / `_drawOrbiters`）**
- 只有一个状态量：**亮度**。把它当电压表画，不当角色画。
- **不读 `this.pose`** —— 不读「患者做错了什么」，就不会被画成有情绪的东西。
- 供能束（光核 → 地平线）是画面因果的关键：没有它，光核就是一块悬在天上的贴纸。
- 核心渐变的白心必须**很窄**（0 → 0.22 → 0.62 → 1）：0.35 处就给满 alpha 会烧成一片纯白，
  结构全没了。这是改这版时实际踩到的。
- 轨道环用**近白色**而不是核心的青绿：同色叠加在同样青绿的辉光上只会更亮一点，
  读不出「有一道环」。

### 12.5 测试契约（也反过来了）

`tools/shoot-ui-test.js` 第 9 节从「哨兵必须真的在动」改成「亮度必须反映进度」：

- 靶心直接取 `m.x / m.y`（红线，一直没变）
- `light = 0 / 0.5 / 1` 三档绘制**必须都不同**（亮度真的跟着进度）
- 同一 `t` / 同一 `light` 两次绘制完全一致（不掺随机）
- **行为验证回路**：塞一颗扫掠线段穿过靶心的子弹，`_collide()` 之后 `light` 必须 > 0
- 光核**不许出现 `this.pose`** —— 它是仪表，不是角色

`tools/scene2d-test.js` 新增第 `[3e]` 节（8 项）：灯数 ≥ 40、`d` 单调升序
（点亮顺序 = 从中心向外）、全部在地平线以上、`light=0` 几乎不画 / `light=1` 点亮全城 /
半亮落在中间、同 `light` 同 `t` 一致、无 NaN。

现状：射击 47 / 界面 **74** / 场景 **90**，16 套全绿。

### 12.6 没做、留给下一步

1. **判定范围仍然不可见**（`targetRadius` 22 vs `hitRange` 60，`showHitArea` 默认关）。

2. `smug` 这个字段名还留着（语义是「出界警戒」），改名会影响 `pose` 侧的事件与存档，
   暂时不动。
3. 结算页遮罩已从 0.72 调到 0.52，让点亮的城透出来；但卡片仍然居中挡住地平线，

## 13. 战机换成离线渲染的 3D 贴图（2026-10-29 深夜）

### 13.1 起因和否决

用户拿来一个 `target_plane.glb`（23.7KB，648 顶点，单材质 `BodyGray`，无贴图）。
用 Blender 渲了正后视 / 3/4 后视 / 侧视三个角度后否决，两个理由：

1. **它是客机**：圆润机头、细长后掠翼、后掠垂尾。这个游戏的语境是"给城市供能"，
   玩家那架机体要有锐度。
2. **后视角度识别度极低**：正后方看只剩「一个椭圆机身 + 两条细横线 + 中间一根竖椭圆
   （垂尾正面）」，像一只飞蛾。而追尾视角是这个游戏唯一用得到的角度。

技术上也确认了一遍：`.glb` **不能运行时加载**。小程序 canvas 只有 2D 上下文，
3D 要 WebGL + three.js + GLTFLoader —— 10 月 29 日已经整体回滚过一次，不重走。

### 13.2 自制模型

`tools/blender/fighter.py`（可重跑）：313 顶点 / 251 面，6 个材质分区。
**设计是针对后视角度倒推的** —— 宽三角翼、双外倾垂尾、双引擎、边条翼（LERX）、
平尾、翼尖挂架、琥珀涂装斜带、机翼面板线。凡是正后方看不见的细节一律不做。

迭代中踩到的四条（都写进脚本注释了）：

1. **引擎中心距必须 > 直径**。第一版 `cx=±0.29`、直径 0.52 → 两个圆叠成一个「8」字。
   改成 `±0.335` / 直径 0.47。
2. **座舱盖小于机身宽 30% 会像一根天线**。从 ±0.17 加到 ±0.24（占 45%）。
3. **背光面不能压到纯黑**（材质 < 0.10）。垂尾内侧在正后视下是完全背光的，
   纯黑会在游戏里读成一个洞。提到 0.19。
4. **翼尖挂架不能悬空**。第一版挂在 `z=-0.28`，而机翼上反后翼尖在 `z=+0.12`，
   中间差 0.4 而机翼只有 0.095 厚 —— 渲染出来是两块飘着的方块。

### 13.3 运行时

- 贴图 306×216 RGBA（67KB），比例**正好是 `_shipBox()` 的 68:48**，
  所以 `drawImage(ship, -hw, -hh, W, H)` 直接铺满，不动任何布局参数。
- **矢量版完整保留**在 `else` 分支作为兜底：贴图没加载完 / 加载失败时自动退回，
  画面不会开天窗。这是从 `sprites.js` 一开始就有的设计，这次沿用。
- **轮廓光**：`shadowColor` + `shadowBlur=4s` 给整张剪影勾一圈冷光。贴图本身没有边缘
  发光，在暗场景里就是一块深蓝；这是它和光柱、光核之间唯一的颜色联系。
- **`SHIP_K = 1.32`**：渲染图里机身上下留了透明边距，1:1 铺满会比矢量版小一号。
  翼尖灯和引擎光的位置都乘了它 —— 改系数必须同步改那三处。

### 13.4 两个必须记住的差异

**引擎位置不同**：
| | 引擎 x | 引擎 y |
| --- | --- | --- |
| 矢量版 | `hw * 0.28`（设计值，为了和机翼比例好看） | `hh * 0.88` |
| 贴图版 | `hw * 0.115`（模型里的真实位置） | `hh * 0.71` |

用错位置，光团会飘到机翼上，变成"机翼在发光"。

**子弹尺寸跟着改**：`36 → 28`。战机换成贴图后整体变宽（90px 翼展），
原来那根 36px 的激光在机翼上像一根插在前面的绿棒子。

### 13.5 体积

主包 800.5 → **867.4 KB**（+67），全包 2036.9 → **2122.4 KB**，余量 >25%。
16 套自检全绿（射击 47 / 界面 74 / 场景 90 / 包体积 11）。

### 13.6 出界变色没做

矢量版原本可以和光核同步转暖红（出界时）。贴图版做不到 ——
`globalCompositeOperation='source-atop'` 会影响整个画布的已有像素，不是只作用于这一张图。

## 15. 倾斜幅度：24° 是贴图的上限（2026-10-30 00:05）

用户要求「绕中心轴的变化再大一点，有刺激感」。试到 **0.46 rad（26.4°）时翻车了**：
侧屈 14° 的截图里，飞机几乎「躺平」，读不出是飞机。

### 15.1 根因：贴图的旋转不是真横滚

真实的横滚是**绕机身纵轴滚**：机翼一侧朝向镜头、另一侧背向，透视会变；
而我们对贴图做的是**在屏幕平面内整张旋转**（`ctx.rotate`）。
后者不会产生任何透视变化 —— 角度一过 ~24° 就露馅，变成「一张纸片在转」。

矢量版不受这个限制，因为轮廓是当帧算出来的。**这是贴图方案唯一的硬伤。**

### 15.2 定在 0.42 rad

| 侧屈 | 线性（初版） | 指数 0.36（上一版） | 指数 0.42（现在） |
| --- | --- | --- | --- |
| 2° | 1.9° | 3.7° | 4.3° |
| 6°（保持区边缘） | 5.8° | 8.4° | **9.8°** |
| 20°（满量程） | 19.5° | 20.6° | **24.1°** |

横向压缩从 `cos(tilt*1.4)` 提到 `cos(tilt*1.5)`，倾斜 24° 时压到 0.85 倍。
**不能再压**：旋转已经吃掉一部分「像实体」的感觉，压缩跟着加码就会扁成一张纸。

### 15.3 如果还要更刺激，只有三条路

1. **多角度贴图**：渲 −20° / 0° / +20° 三张，按 tilt 混合或切换。
   有真实透视，能上到 30°+，代价是体积 ×3（约 +134KB）和混合时的亮度叠加问题。
2. **回矢量版**：轮廓现算，30° 也不失真，但失去 3D 体积感。
3. **加特效而不是加角度**：快速倾斜时给翼尖画速度线、让内外侧引擎光不对称。
   成本最低，但静态截图看不出来，得真机跑才判断得了。

### 15.4 红线不变

倾斜只作用于 `ctx.rotate` / `ctx.scale`。判定仍然是 `playerX` 的纯像素逻辑。
**绝对不能在倾斜里加横向位移** —— 那会让「看到的飞机位置」偏离判定位置，
和「光柱边界 = 判定边界」是同一条红线。

> **本节记录的是一个被回退的方案，不是当前实现。**
> 代码留在 `git stash@{0}`（"A方案：俯冲掠城"），要取回执行
> `git stash apply stash@{0}`，注意它会盖掉现在的蓝调配色。
> 回退的原因不是画面不好看，而是用户选定了另一条路（第 18 节）：
> 俯冲视角把城市从"一排剪影"改成"脚下的街区"，意味着整棵树重画；
> 而当时更想要的是**不动几何、只换时间**。
> 这段留档的价值在于：它解释了"城市为什么不能单纯靠放大"，
> 以及那几个已经踩过的坑（侧墙、窗户比例、地平线雾、点亮的绘制顺序）。

### 17.1 「还是好小」的真正原因

第 14、16 节连着把 `CITY_SCALE` 从 1.16 加到 1.5，用户还是说"好小"。原因不在比例，
在**空间**：城市是地平线上的一排剪影，塔只能长在「光核下沿 → 地平线」这条约 62px 的
带子里。CITY_SCALE 再往上加，塔顶就插进光核。这是个封死的上限。

实测原画面上：一般塔 **19px** 高，天际线整体是一条 24px 的窄带，而天空占了上半屏
364px 里的 210px 是空的。**不是塔不够大，是城市在屏幕上没有地方可长。**

### 17.2 改法：把城市从「地平线」搬到「地面」

`HORIZON_RATIO` 0.52 → **0.40**，取景从"站在远处平视"改成"贴着楼顶俯冲"：

| 层 | 旧 | 新 |
|---|---|---|
| 城市 | 地平线上的一排剪影（`spires`） | 街道两侧由近及远的楼群（`blocks`），24 栋 |
| 地面 | 铺满下半屏的发光网格 | 一条带路缘、车道虚线的街道 |
| 天际线 | `drawRidge` 单独画一排窄峰 | **删除** —— 天际线由楼群自己围出来 |
| 行星 | 左上角一颗紫色带环行星 | **不再绘制**（`drawPlanet` 保留但没调用） |

透视只用一根线：`streetHalfAt(y) = half * STREET_K * (y - horizonY) / (bottom - horizonY)`，
在 `horizonY` 处收成 0 —— 这才是消失点，而不是"一条慢慢变窄的带子"。
`STREET_K = 1.85`：街道比保持区光束宽 85%，楼站在街边而不是光束里。

### 17.3 楼群怎么画

每栋楼只存**世界尺度**参数（深度 `d`、宽 `wN`、高 `hN`、列数、层数），
屏幕坐标由 `blockLayout()` 现算。**不能烘进 `buildScene`** —— 保持区半宽是治疗师
可改的配置，烘进去会在配置变更后失效。

- `baseY = horizonY + floorH * d`，尺寸全部正比于 `d`（近大远小）
- `hN` = **相机高度的倍数**。>1 的塔会探出地平线，这是俯冲视角最直观的"高"
- 每栋楼画两片：正面 + **沿街的侧墙**（往消失点方向退 `rr≈0.7` 倍深度）。
  只画正面的话，街道两侧是两排卡片 —— 看得到楼，看不到街。
- 空气透视：越远越亮越淡（`rgb(5,11,18)` → `rgb(35,53,66)`）。
  夜里的远楼不是黑的，它被整座城市自己照亮。画黑立刻变贴纸。

### 17.4 灯火：点亮单位从「一扇窗」改成「一层楼」

俯冲视角下近处的楼有 500px 高，一扇窗只有 6px，逐窗点亮在手机上根本看不见。
现在一盏灯 = 一栋楼的**一层**（`lamp.b` + `lamp.ly`），全城约 160 层。

**点亮顺序改成「从脚下沿街推向消失点」**。旧版是"离屏幕中心越近越先亮"，
在俯冲视角里越远的楼越靠中间 —— 中心优先会让前几十发全部打在远处几个
几乎看不见的小点上，患者做完一组动作看不到任何反馈。

**一个必须记住的坑**：灯火**必须按楼的深度顺序绘制**，不能按点亮顺序绘制。
点亮顺序是"先近后远"，照着它画会让远处楼的窗盖在近处楼的立面上。
所以分成两张表：`lamps`（点亮顺序）和 `lampByBlock`（绘制顺序）。

### 17.5 过程中试错掉的四个方案

1. **侧墙上也点亮"每层的灯"** —— 用 `stroke` 沿侧墙梯形画横向光带，
   `lineWidth` 取层高。结果满屏斜条纹，像下雨。
   **楼道的墙上不会有横向光带，光是从窗户里出来的。** 改回只画 1px 楼层线。
2. **窗户一次给到层高 34% / 列距 58%** —— 一贴一贴的彩色便利贴。
   收到 19% / 50%，同层各窗亮度差从 0.45~1.0 收到 0.72~1.0。
3. **地平线雾用 `scale(1, 0.042)`** —— 变成一条比上下都亮的横带，在楼群之间
   画出一道"水位线"。摊到 0.10 并减半亮度，才读成"远处有雾"。
4. **不做楼栋级暖光罩** —— 全亮的城是"贴了亮片的黑板"，楼和楼之间没有空气。
   加一层 `0.13 * share` 的径向暖光，整座城才"在发光"（成本 24 次渐变）。

- 视差只作用于星与星云。楼群、路面、光柱一律不平移 ——
  站在地上的东西跟着平移，视觉效果是"地在滑"
- 靶子中心 `MONSTER_Y_RATIO` 0.36 → **0.32**：地平线上移到 0.40 后，
  光核离地平线只有 0.08h（390×700 上约 56px），像"悬在街道尽头"

  从它自己画出的梯形里量出远端/近端半宽，再按同一根线插值核对每栋楼的内缘。
  这样调整 `STREET_K` 不用改测试 —— 它检查的是两层是否一致，不是某个魔法数字。

## 18. 定版：换成蓝调时刻（2026-10-30 00:50）

### 18.1 只换时间，几何一个像素不动

### 18.2 改了什么（全在 `scene2d.js`，全是颜色/强度）

| 层 | 深夜版 | 蓝调版 |
|---|---|---|
| 天空 | `#02040a → #0a1c2b`（单调压黑） | `#0a1636 → #7d6681`（深靛 → 藕紫，**冷在上暖在下**） |
| 地平线辉光 | 青色 `rgba(48,206,186,.155)` | 落日余晖 `rgba(255,178,126,.24)` |
| 侧向光 | 单一暖斑 | 暖斑偏一侧 + **背光侧压冷**（玫瑰紫天光打在楼背面） |
| 星星 | 全屏可见 | 只在靠近天顶处可见（`vis = clamp((1-y/h)*1.9-0.35, .05, 1)`） |
| 星云 | 0.055~0.085 | ×0.28（天光下基本看不见） |
| 行星 | 紫色带环土星 | **淡月**，环彻底去掉（两个 `0`，想恢复改回 0.55/0.85） |
| 地面 | 青绿底 + 青绿网格 | 藕紫底 + 冷紫灰网格（青绿在蓝调里会跳成"科技界面"） |
| 剪影 | `rgba(3,11,18,.94)` 近黑 | `rgba(24,20,48,.93)` 深靛紫（挡住亮天，不能死黑） |
| 地平线雾 | 青色 | 暖粉（太阳刚落下去的那层薄光） |
| 塔尖信号灯 | 青色 | 暖白 |

### 18.3 一条不能画错的规律：冷在上、暖在下

天顶深靛、越靠地平线越亮越暖。这是黄昏后二十分钟唯一不会画错的分布。

- 深夜背景是**等亮度的黑**；蓝调是**一段有方向的渐变**。这就是它一眼不像
  "太空壁纸"的原因 —— 太空图没有光源方向，蓝调有。
- 暖色必须紧紧压在地平线附近，往上迅速退回冷色。暖到中天就成了"暖色滤镜"，
  那是另一种 AI 味。

### 18.4 地平线不能是一条硬边

第一版地面渐变的头一档是 `rgba(104,94,120,0.72)`，比天空底部暗一截 ——
地平线立刻变成一条清晰的横线，上下像两张图拼在一起。

**地面渐变的第一档必须等于天空最底下那个颜色**（`rgba(125,102,129,0.86)`），
往下四档慢慢压暗。这一条比任何"加雾""加暗角"都管用。

### 18.5 已知短板（选 B 的代价，改不了）

城市仍然是地平线上的一条窄带，一般塔 **19px** 高 —— 第 17.1 节算过，
这是"平视取景 + 光核位置"共同决定的上限，只换颜色不会让它变大。
蓝调只是让这条带子**看得更清楚**（亮天 vs 深靛剪影，对比度比深夜高得多）。

## 19. 把地平线做弯，删掉地面网格（2026-10-30 01:20）

### 19.1 起因：用户说「感觉好多的线」

清点下来画面上一共约 **30 条**几何直线：

| 来源 | 条数 |
|---|---|
| 地面网格 | 9 纵 + 11 横 = 20 |
| 保持区 | 光柱 2 竖 + 地面通道 2 斜 = 4 |
| 瞄准虚线 | 1 |
| 地平线 / 城市基座 | 2 |
| 城市剪影 | 30+ 根竖窄条（远看是条形码） |

根本原因不是"背景选得不对"，而是**整个纵深是用线框（wireframe）表达的**。
天空本该用"面"和"体"来表现。

### 19.2 做法：只改两件事

1. **地平线变弧**：`HORIZON_CURVE = 0.045`（390 宽上约 17px），
   `horizonYAt(x) = horizonY + w * 0.045 * u²`，u = -1..1。
   这是"高空俯视地球边缘"的取景，一句话把"我站在地上"变成"我在很高的地方"，
   而且**不新增任何直线**。
2. **删掉地面网格**，换成 7 条**沿着弧线向前滚的雾带**（`fillHorizonBand`）。

### 19.3 关键取舍：网格不能单纯删掉

网格是画面上唯一的**速度参照物**。光删它，地面变成一块静止的黑板，比原来更不像在飞。

所以换成"雾带"而不是"什么也不画"，而且要满足两条才不读成线：
- **没有描边**，是填充带；
- **边缘靠两层 alpha 台阶散开**（外层 2.8 倍厚、alpha 0.32），不是一条实边。

滚动相位沿用旧的透视关系 `y = horizonAt(x) + floorH / u`（u 递减即向前滚）。

### 19.4 三个必须跟着弧走的层

`fillHorizonBand()` 是所有弧形层的唯一入口。任何一层不跟着弧：
- **地面**：`fillRect(0, hz, w, floorH)` 会在弧的两端露出直角；
- **城市基座 / 塔基**：每根塔的脚必须踩在**它脚下那一点**的 `horizonYAt(bx)` 上，
  用统一 `hz` 会让塔一半悬空一半埋进土里；
- **窗灯 / 街道灯**：同理，`hz - ny*w` 要换成 `horizonYAt(x) - ny*w`。

还有一个隐藏坑：路径的**收尾**。`lineTo(x1, hz+2)` 这种直线回程会在弧上切一刀，
必须沿弧走回去（`for (x = x1; x >= x0; x -= 6) lineTo(x, horizonYAt(x))`）。

### 19.5 测试 `[3f]`

弧线没有任何运行时保护 —— 改回 `fillRect` 不会崩、不会有 NaN，画面只是悄悄变回平视。
所以量出来钉住三件事：

1. 天际线两端比中间低 ≥10px（实测 17.2px），左右对称；
2. 地面的上沿和天际线用的是**同一条弧**（差值 <2.5px）——
   这一条防的是"两层各算各的"；
3. 地面 `stroke` 次数 ≤2（网格必须已经不在了）。

### 19.6 结果

线从约 30 条降到 5 条（光柱 2 竖 + 地面通道 2 斜 + 瞄准 1 虚线），
全部集中在保持区上。地平线两端下垂 17px，城市剪影贴着这条弧，
读起来是"飞在城市上空"，而不是"站在地上看远处"。

**没解决的**：地面通道那两条斜边和光柱的两条竖边还在，它们就是判定范围，
是医疗红线，删不掉 —— 只能继续想办法把它们画得更"像光"而不是"像框"。

## 20. 回到深夜配色，并把光柱的边做成「光的边缘」（2026-10-30 01:45）

### 20.1 第 18 节的蓝调时刻被回退

用户看过蓝调版本之后说「还是黑夜好一点」。**留深夜** —— 这不是说蓝调失败，
而是「天还有光」这件事在这个游戏里不成立：这是个睡前/白天都能做的训练，
一片深色的背景反而让灯火和保持区更跳。

- 天空回 `#02040a → #0a1c2b`，地平线回青色辉光，星云恢复、星星恢复全屏可见
- 剪影回 `rgba(3,11,18,.94)`
- 地面回青绿系，但**保留了第 18.4 节学到的规则**：第一档必须等于天空最底下那个颜色
  （这里是 `rgba(10,28,43,.88)`），否则弧的两端会露出硬边
- 月亮保留（环仍然是 0，不恢复土星环）

蓝调的完整色值留在第 18 节，想换回去照抄即可。

### 20.2 保持区边界：等宽亮带 → 四层光晕

第 19 节之后画面上只剩 5 条直线，其中最难看的还是光柱那两条竖边。
它们的问题是**等宽 + 内外都是硬边**，这两个特征加在一起就是「选中框」。

改成四层，全部在边界**外侧**：

| 层 | 宽度 | 峰值 alpha | 分段 |
|---|---|---|---|
| 芯 | 1.3px | 1.00 | 26 |
| 近晕 | 8px | 0.30 | 12 |
| 中晕 | 22px | 0.12 | 8 |
| 远晕 | 46px | 0.05 | 6 |

两条附加规则：
- **越靠下越宽**（`w * (0.66 + p * 0.5)`）：光源在地面上，底下的光自然铺得开。
  等宽是「框」最强的信号，因为真实的光不会上下一样宽。
- **芯永远在 `cx ± half` 上，且在任何画质下都是满分段**。
  光可以向外散，不能向通道里散 —— 往里渗一像素都是在骗患者。

降档：`quality 0` 砍掉中晕/远晕，`quality 1` 分段 ×0.6。四层全开是 104 次填充，
低端机上不便宜，所以引擎把 `quality` 传进了 `drawKeepPillar`。

### 20.3 地面通道的两条边：改成会消失的线

原来用固定 `rgba(core,0.18)` 描两条从脚下直拉到消失点的斜边 ——
亮度不变、长度到底，读起来就是「画上去的线」。

改成纵向渐变描边（脚下 0.30 → 45% 处 0.12 → 消失点 0），
两条边在半路就散光了，只剩下脚下的那一截。**会消失的线才像光。**

### 20.4 一个放大后才看得见的坑

地面雾带的外晕和芯用了同一个 `offTop`，导致外晕的上沿形成一道比芯更亮的台阶，
6 倍放大下是一圈明显的横纹。**外晕必须居中于芯**（`off - th * 0.9`）。

## 21. 地平线以下改成水面（2026-10-30 01:55）

### 21.1 为什么是水

第 19 节把网格删掉之后，地平线以下只剩一片纯暗的渐变，两侧两个大三角什么都不发生。
用户选的下一件事就是「水面反光」—— 这是这片空白最省也最对的填法：

- 它给了**下半屏内容**，而且不需要新的几何（不用再画线）；
- 它让画面第一次**上下对称**：城在天上亮，灯火在水里有下半截；
- 它把「我在飞」变成了「我在水上方飞」，比单纯的高空更有位置感。

### 21.2 三层，缺一层就不像水

| 层 | 作用 |
|---|---|
| 水面天光 | 贴着弧线的一道冷色亮带，往下迅速散尽。没有它，倒影会浮在黑布上，读成「地上几个亮点」 |
| 城市整体倒影 | 一条**连续**的暖带（0~0.085 floorH + 0.085~0.15 衰减）。这是水成立的关键 |
| 碎光竖条 | 逐灯的竖向拉丝，提供「碎」的质感 |

**只画竖条会变成一排栅栏。** 真实照片里贴着水天线的永远是一片糊在一起的橙，
不是一根根柱子 —— 所以先铺连续暖带，竖条只负责在暖带上打碎。

### 21.3 竖条的四个参数

1. **长度逐灯不同**（`0.3 + hash*0.7`）。所有灯拿同一个 base 时，每道倒影一样长，
   整片就是一排等距栅栏 —— 这个坑第一次做的时候踩了。
2. **二次衰减** `base * (1 - fr) * (1 - fr*0.35)`。线性衰减读成「一根均匀的柱子」。
3. **长度上限只有 0.22 floorH**。再长就成了「竖着的灯柱」，倒影是贴着光源的一小截。
4. **段间留 14% 的缝** + 水平方向按 `sin(t + x*0.075)` 摆动 —— 缝和摆就是波纹。
   相位跟 x 走，相邻两盏不同步；同步的话整片一起晃，像一块布在抖。

保持区光柱有自己的一条倒影（以 cx 为中线，越远越宽），光核正中还有一条最窄最亮的。
没有它们，光柱的倒影会读成「一根柱子插在水里」，而光核才是水源。

### 21.4 成本

每 2 盏灯取 1 盏 → 每 3 盏（stride 3）。stride 2 会到 270+ 次填充，
和光柱的四层光晕叠起来低端机顶不住。降档：quality 1 用 5，quality 0 用 9。

### 21.5 测试 `[3g]`（7 项）

倒影唯一可信的条件是「挂在光源正下方」，偏一两像素就从「倒影」变成「光斑」，
而且没人会立刻发现 —— 只是觉得水面有点脏。所以量：

1. `light=0` 一条不画（倒影是灯火的下半截，不是另一套装饰）；
2. `light=1` >60 段，`light=0.5` 更少（跟着 light 长）；
3. 全部在地平线以下（飘到天上就是另一个 UI 层）；
4. 保持区那条以 cx 为中线；
5. 每一段竖条的中心都能在灯火里找到对应的 x（容差 6px），命中率 >95%。

## 22. 界面去「假」：八处（2026-10-30 02:10）

用户反馈「有点丑丑的，怪怪的，不真实」。整屏截图逐轮评审，一共定位到八处。

共同点值得记下来：**每一处「假」都是同一个病因 —— 某个本该连续变化的东西被画成了恒定值。**
恒定的颜色 → 平的；恒定的亮度 → 贴纸；恒定的宽度 → 框。

### 22.1 光核：从「白盘子」改成光源

原样是 3 道 210° 的粗环 + 一个过曝的白心，读起来是一个白瓷盘。

改成：2 道 120° 的 1px 细环 + 一个小亮点（半径 10% 内）+ 一层大柔光（`cr*2.2`）。
受击闪白减半（`min(0.28, m.sad*0.40)`）。

### 22.2 HUD：删掉玻璃卡片

原来得分 / 倒计时各装在一张圆角玻璃卡片里（上浅下深的底 + 顶部高光 + 细描边 + 顶边反光）。
这套东西直接来自手游模板，画面里最「UI」的就是它。

改成：顶部一层压暗 scrim（`0.58 → 0.22 → 0`）+ 细字重（300）的仪表读数。
不画任何卡片、不画描边。`_glassCard` 随之成为死代码，已删除。

### 22.3 月亮：整颗球均匀受光 = 一只灯泡

原样是径向渐变从左上高光到右下暗面，但边缘 alpha 仍有 0.90（硬边），
而且**整颗球都被照亮** —— 没有明暗界线，这就是「灯泡」感的全部来源。

改成：夜面打底 `rgba(44,54,84,.96)`，受光面用**从光源点发散**的径向渐变，
0.52 → 0.635 之间陡降形成 terminator。加了 2 片月海（大暗斑）+ 4 个环形山
（只在受光面可见，暗面里 `lum<=0.12` 跳过），最后叠一层边缘限暗。

外辉光从 2.6r 收到 2.0r —— 2.6r 会散成一团雾。

> 只有小坑没有月海，读起来是一颗高尔夫球。

### 22.4 倾角文字：青绿不能给 UI

区内原本是 `rgba(125,255,207)`。这违反了自己定的规则 ——
**青绿是保持区的专属色**，UI 占用了患者会分不清哪个才是判定范围。
改成淡蓝白 `rgba(214,232,250,.95)`。出界仍用红。

### 22.5 城市剪影：所有塔一个颜色 = 一条死黑的条形码

原来全部塔共用一个 `rgba(3,11,18,.94)`，一次 fill 画完 → 完全平。

加空气透视分三档（`s.band`，由远及近三趟画，近档压住远档形成遮挡）：

| band | 填充 | 高度 × | 塔灯 alpha |
| --- | --- | --- | --- |
| 0 远 | `rgba(12,32,48,0.70)` 淡、偏蓝 | 0.70 | 0.24 |
| 1 中 | `rgba(6,19,29,0.88)` | 0.86 | 0.38 |
| 2 近 | `rgba(2,7,12,0.96)` 暗、高 | 1.00 | 0.50 |

两个坑：
1. **缩放必须乘进 `s.h` / `s.w` 里**（生成时就乘），不能只在绘制时改高度 ——
   否则 `drawCityLights` 的窗灯还按原高度算，窗会飘到塔身外面。
2. **相邻两根塔要同档**（用 `i >> 1` 做 hash，不是 `i`），街区才成片。
   每根塔随机深浅会变成噪点，不是纵深。

### 22.6 光柱的外两层晕：0.12 / 0.05 等于没画

四层光晕里最外两层原本是 `{w:22,a:0.12}` / `{w:46,a:0.05}`。
在深色天空上这个量级**根本看不见**，于是边界退化成一根孤立的亮线 ——
评审两次都是同一句评价：「像两根画出来的线」。

提到 `{w:28,a:0.26}` / `{w:64,a:0.14}`，加宽的同时提亮，才真正出现光晕。

**芯（判定边界）一行没动**：位置仍严格等于 `cx ± half`，光仍只往外侧散。

### 22.7 地平线曲率 0.045 → 0.062

0.045 在 390 宽上只有 17px 下垂，放到 720 高的整屏里读不出来 ——
两轮评审都被说成「地平线是一条直线」，等于白做。
0.062 约 24px，肉眼能看出两端下垂，仍不到鱼眼。

### 22.8 地面通道：只有纵向渐变 = 一块三角形色纸

梯形原来只有纵向渐变，横向没有衰减，所以两条斜边是硬边 →
「贴在地上的三角形色纸」，是整屏最出戏的一处。

改成：clip 进梯形后分 10 段，每段用**横向**渐变（中心 0.76 → 两侧 0），
纵向衰减用 `globalAlpha` 控制（`0.05 + (1-p)^1.6 * 0.95`）。
与光柱主体同一套做法。

判定用的两条斜边线（纵向渐变，脚下 0.30 → 消失点 0）保留不动。

### 22.9 保持区标签：11px 无描边

「保 持 区 ±6°」压在天空 / 城市剪影 / 光柱上，背景亮度跨度很大，
11px 细字不描边会在亮处发虚。加了 3px 暗色描边，字号 11 → 12。

### 22.10 测试

`tools/scene2d-test.js` 104 项、`tools/shoot-ui-test.js` 74 项，改动后全绿。

本轮**没有新增断言** —— 上面八处全是审美判断，行为断言钉不住，
硬钉只会把参数写死成不能改。留档在这里靠文档约束。

### 22.11 预览的两个坑（本轮踩到）

1. **esbuild 在 `tools/` 下写文件会被拦**（Access denied），
   必须 `write:false` 取回 buffer 由 Node 落盘。临时脚本 `tools/shoot-preview/_build.tmp.js`。
2. **`--screenshot` 必须给绝对 Windows 路径**（`E:\...`），
   给 `shots/xxx.png` 这种相对路径会报「系统找不到指定的路径」，且不产生任何文件。
3. **`state=paused` 截不到画面** —— 暂停遮罩会盖住整个场景。想看背景/光柱要用 `state=running`。

## 23. 城市第三次放大：换分布，不是换倍数（2026-10-30 16:30）

用户圈出画面中部一条约 11% 屏高的横带：「城市放大到红框那么大」。

### 23.1 前两次为什么没解决

前两次都是加 `CITY_SCALE`（1.0 → 1.16 → 1.5），结果用户三次说「还是好小」。
测出来根因不在倍数，在**分布形状**：

| 指标 | 旧分布 `0.012 + r²×0.060` |
| --- | --- |
| 最高塔 | 72.7 px |
| **中位塔** | **11.6 px** |
| 最矮塔 | 5.1 px |

天际线的主体是「中位塔」，而中位塔只有 11.6px —— 患者看到的是贴在地上的一排小点，
最高那根 72.7px 是孤零零一根尖刺。加倍数只会让那根尖刺更快插进光核，
而主体依然趴着。这就是「怎么加都还是小」的全部原因。

### 23.2 改法

1. **换分布**：`0.055 + r^1.5 × 0.075`（底数从 0.012 抬到 0.055 把整排楼拔离地面，
   指数从 2 降到 1.5 收窄高低差，避免底数一抬最矮塔也跟着变高、天际线拉平）
   → 中位塔 36px、最高 93px、最矮 21px。
   （中间试过 `0.010 + r^1.2 × 0.16`：长尾太散，中位仍只有 31px，且最高塔冲到 121px 撞光核。）
2. **光核上移** `MONSTER_Y_RATIO` 0.36 → 0.33：可用高度从 90px 涨到 114px，
   才装得下 93px 的塔。
3. **塔距 10 → 9px、跳过率 0.22 → 0.14**：城市变高后，稀疏细柱读成「一圈篱笆」。
   楼群要连绵，相邻塔必须基本相接，只在少数位置留缺口。
4. **塔宽 ×1.5**：3~7px 的细柱读成「电线杆」，楼群要有体量。
5. **尖顶比例 28% → 10%**：尖顶扎堆会读成「一圈山」而不是城市。
   真实天际线绝大多数是平顶楼，尖塔只是点缀。
6. **窗间距 4.5 → 8.0**：城市放大后灯数从 ~150 涨到 214，而一局只有 180 发 ——
   一局打不满整座城，「点亮一座城市」的反馈会打折。回到 172 盏。

### 23.3 结果

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 最高塔 | 72.7 px | 93 px（12.9% 屏高） |
| 中位塔 | 11.6 px | 36 px |
| 最矮塔 | 5.1 px | 21 px |
| 灯数（390 宽） | ~150 | 172 |
| 塔顶与光核下沿余量 | 22 px | 22 px |

余量没变是因为光核同步上移了 —— **这两个数字是一起定的，改一个必须重算另一个**。

### 23.4 新增守护断言（`tools/shoot-ui-test.js`）

- 最高塔顶必须在光核下沿以下（390×720 / 414×896 / 320×568 三种尺寸）；
- 城市高度不得低于 7% 屏高（防止有人把放大效果改回去）。

### 23.5 方法论

**「放大一个东西」失败三次之后，不要再调倍数，去看它的分布。**
前两次都在调 `CITY_SCALE`，但用户感知的是「中位高度」，而中位数由分布形状决定。
倍数只改变量纲，形状才改变感知。

同类教训在本文档里已经出现过两次：城市「平」（所有塔共用一个颜色 → 改空气透视三档）、
光柱「像画的线」（外晕 alpha 0.05 等于没画 → 提到 0.26）。
**都是「参数调了很多次但模型错了」，正确做法是先量分布，再改形状。**
