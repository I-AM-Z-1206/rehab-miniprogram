## 一、图片资源：默认打包，不要放服务器

这是最容易做错的一步。**游戏图片放服务器，在这台机器上会明显拖慢体验。**

### 算笔账

那台 ECS 的公网带宽通常是 **1~5 Mbps**（具体值在阿里云控制台"实例 → 带宽"看）。按 2 Mbps 算：

| 图片 | 大小 | 下载耗时 |
| --- | --- | --- |
| 一张 750×1334 的 WebP 背景 | 250 KB | ≈ 1 秒 |
| 一个游戏的 10 张素材 | 2.5 MB | ≈ 10 秒 |
| 5 个游戏全量 | 12 MB | ≈ 50 秒 |

家用场景里，患者点开游戏先等 10 秒黑屏 —— 这个体验比"包大 2MB"糟糕得多，而且依从性本来就低。

### 你现在的分包余量

| 包 | 现在 | 上限 | 还能放 |
| --- | --- | --- | --- |
| 主包 | 0.83 MB | 2 MB | **1.17 MB** |
| pkgRhythm | 0.49 MB | 2 MB | 1.51 MB |
| pkgFruit | 0.21 MB | 2 MB | 1.79 MB |
| pkgWire | 0.17 MB | 2 MB | 1.83 MB |
| pkgShoot | 0.04 MB | 2 MB | 1.96 MB |
| pkgRace | 0.10 MB | 2 MB | 1.90 MB |

**完全不缺空间。** 每个游戏再加 3~5 张背景图都放得下。

### 该打包还是该上服务器

| 资源 | 放哪 | 原因 |
| --- | --- | --- |
| 图标、按钮、tabBar | 主包 `assets/` | 首屏就要，几十 KB |
| 游戏场景背景、立绘、贴图 | 对应分包 `pkgXxx/images/` | 进游戏才下载，**离线可用** |
| 音效、BGM、音轨 | 对应分包（现状已是） | 同上 |
| **节日皮肤、运营活动图** | 服务器 / OSS | 要不发版就换 |
| **单张 > 500 KB 的整屏插画** | OSS + CDN | 进包会挤占分包额度 |
| **要给小程序外复用**（公众号、H5） | OSS + CDN | 包外要用 |
| **用户上传**（头像、训练视频） | OSS 私有读 + 临时 URL | 不能进包，要权限控制 |

**判断规则就一句：这张图会不会不发版就换？** 不会 → 打包。会 → 服务器。

### 打包的具体规范

1. 尺寸按 2 倍图做（750×1334 或 780×1688），导出 **WebP 质量 80**，单张控制在 250 KB 内。
2. 放 `pkgFruit/images/`、`pkgRhythm/images/` 这样，跟着分包走。
3. Canvas 里加载：
   ```js
   const img = canvas.createImage()
   img.onload = () => { this.sceneImg = img; this.bg = null }  // 触发离屏重绘
   img.onerror = () => { this.sceneImg = null }                // 失败回退程序化背景
   img.src = '/pkgRhythm/images/scene-garden.webp'
   ```
   **必须做 onerror 回退**：加载失败时用现在的程序化背景兜底，不能白屏。
4. 图片来源和授权留痕：`pkgXxx/CREDITS.md` 写作者/许可/链接。

### 如果确实要放服务器

**不要在 Node 里做 `/static` 转发**，让 nginx 直接托管文件，性能高一个量级：

```nginx
# 追加到 rehab-api.conf 的 server 块里
location /img/ {
    alias /opt/rehab/images/;
    expires 30d;
    add_header Cache-Control "public, max-age=2592000";
    access_log off;
    try_files $uri =404;
}
```

配套要求：

- **文件名带版本号**（`bg-garden-v3.webp`），才敢设长缓存。换图就改版本号，不发版也能生效。
- 目录 `/opt/rehab/images/`，**不要放 `/www/wwwlogs` 或 `wwwroot`**。
- 注意微信规则：**小程序正式版只允许 https 加载**。现在这台机器只有 http，所以**备案期间从服务器加载图片在体验版会失败**，只有在开发者工具/真机调试模式才通。
  → 这又是一条"图片应该打包"的理由。

## 二、数据库：SQLite（node:sqlite），不装 ORM

> **已经建好了**：`/opt/rehab/data/rehab.db`，160 KB，10 表 + 3 视图。
> SQLite 不需要安装任何数据库服务，**也没有端口、用户名、密码** —— 它就是一个文件。
> 这也意味着：**不用去阿里云买 RDS / 云数据库**，那是给需要独立数据库进程的场景用的。

已经实测：服务器 Node **v24.21.0**，`require('node:sqlite')` 直接可用，**不需要任何启动标志**，空跑 RSS 46 MB。

### 为什么不是 MySQL / PostgreSQL

| 项 | SQLite | PostgreSQL |
| --- | --- | --- |
| 额外进程 | **0**（嵌在 Node 里） | 1 个（+100~150 MB 内存） |
| 安装配置 | **不用装** | 要装、要建库建用户、要配连接池 |
| 备份 | **拷一个文件** | `pg_dump` + 定期恢复演练 |
| 你现在的量级 | 每天几十~几百条 | 完全过剩 |
| 服务器余量 | 可用 780 MB | 装上就开始吃 swap |

**答案：SQLite。** 什么时候换 Postgres：记录 > 5 万条 / 要多实例 / 要对接医院 HIS。`store.js` 只有 `add/list/stats` 三个方法，换实现只改一个文件。

### 不要上 ORM

表就 10 张，核心查询是聚合报表（`GROUP BY patient_id, week`）。Prisma / Drizzle 在这个场景是负资产：

- 多一层 schema 定义要同步维护
- 聚合查询写成 ORM 语法反而更难读
- 生成 client、迁移工具，都是额外的心智负担

**直接用 SQL。** 需要时加一层薄封装（20 行）：

```js
// server/db.js
const { DatabaseSync } = require('node:sqlite')
const path = require('path')
const fs = require('fs')

const file = path.join(process.env.DATA_DIR || '/opt/rehab/data', 'rehab.db')
fs.mkdirSync(path.dirname(file), { recursive: true })

const db = new DatabaseSync(file)
db.exec('PRAGMA journal_mode = WAL')
db.exec('PRAGMA foreign_keys = ON')     // ★ 每个连接都要设，不是持久化的
db.exec('PRAGMA busy_timeout = 5000')   // 写冲突时等待而不是立刻报 SQLITE_BUSY

// 首次启动自动建表
if (!db.prepare("SELECT name FROM sqlite_master WHERE type='table' AND name='record'").get()) {
  db.exec(fs.readFileSync(path.join(__dirname, 'schema.sql'), 'utf8'))
}

module.exports = { db }
```

用法（预处理语句，天然防注入）：

```js
const stmt = db.prepare('INSERT OR IGNORE INTO record (id, patient_id, game_id, started_at, duration_sec, metrics, config_snapshot, data_source, created_at) VALUES (?,?,?,?,?,?,?,?,?)')
const info = stmt.run(rec.id, rec.patientId, rec.gameId, rec.startedAt, rec.durationSec, JSON.stringify(rec.metrics), JSON.stringify(rec.configSnapshot), rec.dataSource, Date.now())
// info.changes === 0 → 说明 id 已存在（幂等命中）
```

`INSERT OR IGNORE` + `info.changes` 这一招直接替代现在 `store.js` 里手写的去重逻辑，而且是在数据库层面原子的。

## 三、框架：上 Fastify

### 先明确判断标准

| 情况 | 建议 |
| --- | --- |
| 接口 < 10 个，不做文件上传，单人可以裸 http | 继续现在这样，只拆模块 |
| **接口 20+，有登录、有上传、有参数校验** | **上 Fastify** |

你现在是第二种：要加 JWT、患者档案、配置下发、报表、可能还有图片上传。

### 为什么是 Fastify，不是 Express / Nest

| 方案 | 额外内存 | 判断 |
| --- | --- | --- |
| 裸 `http`（现状） | 0 | 4 个接口时挺好，20 个接口 + 上传会越来越痛苦 |
| **Fastify 5** | **+15~25 MB** | **推荐** |
| Express 5 | +20 MB | 生态最大，但校验、上传、JWT 都要自己接中间件，性能约为 Fastify 的 1/3 |
| NestJS | +60~80 MB | 要 TS + 装饰器 + 依赖注入，这个规模纯属负担 |

Fastify 对这个项目的四个具体好处：

1. **内置 JSON Schema 校验** —— 直接替代现在手写的 `sanitize()`（`index.js:85`）和 `validateRecord()`（`index.js:104`）。字段类型、必填、长度、枚举，声明式写清楚，校验失败自动返回 400，且**只保留 schema 里声明的字段**（比手写白名单更严格，不会漏）。
2. **`@fastify/multipart`** —— 如果以后要传图片/视频。**手写 multipart 解析是安全事故高发区**（边界处理、文件名穿越、超大文件），不要自己写。
3. **`@fastify/jwt`** —— 微信登录后签发的 token，`request.jwtVerify()` 一行搞定，`request.user` 直接拿到 role/uid。
4. **性能与内存都合适**：比 Express 快 2~3 倍，内存只多 15~25 MB。服务器剩 780 MB，完全够。

### 迁移成本

现有 4 个接口的**业务逻辑不用动**，只重写路由层。`tools/server-smoke-test.js` 的 18 项断言可以整套复用（它打的是 HTTP，不关心服务端用什么框架）。

预计 1~2 小时。

### 骨架示例

```js
// server/app.js
const Fastify = require('fastify')

const app = Fastify({
  logger: { level: 'info' },   // 生产用 pino，自带结构化日志
  bodyLimit: 256 * 1024,
  trustProxy: true             // ★ 在 nginx 后面，要信任 X-Forwarded-For
})

app.register(require('@fastify/cors'), { origin: false })  // 小程序不走浏览器，可关
app.register(require('@fastify/jwt'), { secret: process.env.SESSION_SECRET })

app.get('/health', async () => ({ ok: true, ts: Date.now() }))

// 记录上报：schema 校验直接写在这里
app.post('/api/v1/records', {
  onRequest: [app.authenticate],
  schema: {
    body: {
      type: 'object',
      required: ['recordId', 'patientId', 'gameId', 'startedAt', 'durationSec', 'dataSource'],
      properties: {
        recordId:     { type: 'string', pattern: '^[A-Za-z0-9_-]{4,64}$' },
        patientId:    { type: 'string', minLength: 3, maxLength: 64 },
        gameId:       { type: 'string', enum: ['fruit', 'wire', 'rhythm', 'shoot', 'race'] },
        startedAt:    { type: 'integer', minimum: 1000000000000 },
        durationSec:  { type: 'number', minimum: 0, maximum: 3600 },
        score:        { type: 'integer' },
        accuracy:     { type: 'number', minimum: 0, maximum: 1 },
        metrics:      { type: 'object' },
        configSnapshot: { type: 'object', required: ['version'] },
        dataSource:   { type: 'string', enum: ['sensor', 'simulation'] },
        interrupted:  { type: 'boolean' }
      },
      additionalProperties: false   // ★ 多余字段直接拒绝，不用手写白名单
    }
  }
}, async (request, reply) => { /* ... */ })

app.listen({ port: 8787, host: '0.0.0.0' })
```

`trustProxy: true` 和 `additionalProperties: false` 是两个容易漏的点：前者让日志里的 IP 是真实客户端而不是 127.0.0.1，后者替代手写 sanitize。

### 依赖安装

```bash
cd /opt/rehab && npm i fastify @fastify/jwt @fastify/multipart @fastify/cors
```

体积约 10~15 MB（含依赖树）。**不要装 `@fastify/static`** —— 静态文件交给 nginx。

### 微信开发者工具设置

1. 打开小程序项目 → 右上角 **详情** → **本地设置**
2. 勾选 **「不校验合法域名、web-view（业务域名）、TLS 版本以及 HTTPS 证书」**
3. 用 **「真机调试」**（不是「预览」）→ 扫码
4. 手机打开后，点右上角 `···` → **打开调试**（出现绿色 vConsole 才生效）

第 3、4 步是关键：**只有真机调试模式 + 手机端开启调试，才会忽略域名校验。**「预览」模式下 http 请求仍然会被拦。

### 小程序端配置

```js
// utils/api.js
const BASE_URL = 'http://47.112.18.198/api'

function post(path, data) {
  return new Promise((resolve, reject) => {
    wx.request({
      url: BASE_URL + path,
      method: 'POST',
      data,
      header: { 'content-type': 'application/json' },
      timeout: 10000,
      success: (res) => resolve(res),
      fail: reject
    })
  })
}
```

备案后只改 `BASE_URL` 一处。

### 必须提前知道的三个坑

**坑 1：体验版和正式版一律不走 http。**
微信的规则是硬的：`request 合法域名` 必须 HTTPS + 已备案。这意味着**备案期间你没法发体验版给治疗师测试**，只能自己在开发者工具/真机调试里看。

如果这周就要给治疗师看，要么加快备案，要么让治疗师用微信开发者工具（需要把他加成开发者）。

**坑 2：图片从 http 服务器加载，在体验版同样被拦。**
这是"图片要打包"的又一个理由 —— 打包的图不受任何网络域名限制。

**坑 3：502 / 404 要分清责任。**

| 现象 | 原因 |
| --- | --- |
| 502 Bad Gateway | nginx 通了，但 8787 没有服务在跑 |
| 404 | 路径不在 `/api/` 或 `/health` 下，被 `location /` 拦了 |
| 请求超时 | 阿里云安全组没放 80（但实测是通的） |
| `request:fail url not in domain list` | 没勾"不校验合法域名"，或手机没开调试模式 |

## 五、部署命令（服务端写完后的完整流程）

```bash
# 1. 建目录
mkdir -p /opt/rehab/{server,data,logs,images,backup}
cd /opt/rehab

# 2. 上传代码（本机执行）
scp -r server/* zzyuan:/opt/rehab/server/
scp package.json ecosystem.config.js zzyuan:/opt/rehab/

# 3. 服务器上装依赖
cd /opt/rehab && npm i --omit=dev

# 4. 建表
sqlite3 data/rehab.db < server/schema.sql

# 5. 启动（PM2，单实例）
pm2 start ecosystem.config.js
pm2 save
pm2 startup systemd -u root --hp /root    # 开机自启

# 6. 验证
curl http://127.0.0.1:8787/health
curl http://47.112.18.198/api/health      # 走 nginx

# 7. 看日志
pm2 logs rehab-api --lines 50
```

`ecosystem.config.js` 的 `instances` **必须是 1**：SQLite 的 WAL 支持并发读，但写是串行的，开 cluster 会在写入竞争时拿到 `SQLITE_BUSY`。

### 备份（配一次，之后不用管）

```bash
# 每天 3:07 备份，保留 14 天
7 3 * * * sqlite3 /opt/rehab/data/rehab.db ".backup '/opt/rehab/backup/rehab-$(date +\%F).db'" && find /opt/rehab/backup -name 'rehab-*.db' -mtime +14 -delete
```

`.backup` 是在线备份，不锁表、不会读到半个写，比直接 `cp` 安全。

## 六、记录归属与账号隔离（2026-10-28 修复）

### 出过的问题

训练记录原本存在固定的 storage 键里（`wire_records_v1` / `fruit_records_v1` / `rhythm_records_v1`），**跟当前登录的是谁无关**。

小程序的 storage 是**设备级**的，不是账号级。所以同一台设备换人登录后：

| 后果 | 严重度 |
| --- | --- |
| 新账号在记录页看到上一个人的记录 | 用户直接可见 |
| A 未上传的记录被 B 的 `flushAll()` 用 **B 的 token** 上报，脏数据记到 B 名下 | **更严重，且不可逆** |

服务端一直是对的（`patientId` 从 JWT 推导），问题全在客户端。当时的端到端自检只验了「服务端不串」，没验「客户端本地不串」，是测试盲区。

### 三层防御

```
① 存储键按账号隔离
   wire_records_v1:p_xxxx   ← 每个 patientId 一个键
   wire_records_v1:anon     ← 未登录时的暂存
② 每条记录带 owner 戳
   上报前核对 owner === 当前 patientId，不一致直接拦下（state='foreign'）
③ 服务端校验 ownerId
   payload 带 ownerId，与 JWT 的 patientId 不符 → rejected: owner-mismatch
```

第 ③ 层是最后一道防线：即使客户端状态错乱，也传不出别人的记录。

### 升级后的行为

旧的固定键记录、以及登录前产生的 `:anon` 记录，会在**下次登录成功后自动归到当前账号名下**（`migrateStores()`，由 `app.js` 的 `bootCloud()` 调用）。

迁移只发生一次，之后就靠键隔离。

> **注意**：如果你在这台设备上切换过多个账号做过测试，那些旧记录的归属已经无法分辨 —— 迁移时会被归给「当前登录的那个人」。测试期的数据建议直接清掉重来（开发者工具 → 清缓存 → 清除数据缓存）。

### 验收

```bash
node tools/record-isolation-test.js    # 18 项
```

覆盖：A 存两条 → 换 B 登录看不到 → B 存自己的 → 切回 A 仍在 → 别人的 owner 被拒且不发请求 → 旧键与 anon 记录迁移且不重复迁移。

### 上线前必须做的三件事

1. **配 `WX_APPID` / `WX_SECRET` 并关闭 `DEV_LOGIN`**
   现在开着开发登录，任何人都能伪造身份。虽然有 80 端口但没真实数据，风险可控，**不能就这么上线**。
2. **备案域名 + HTTPS**
   小程序体验版/正式版必须有 https 域名。备案下来后把 `rehab-api.conf` 的 `server_name` 改成域名、加 `listen 443 ssl`，小程序只改 `utils/api.js` 的 `DEFAULT_BASE`。
3. **治疗师账号**
   用 `THERAPIST_OPENIDS` 指定真实治疗师的 openid。开发期的 `<devId 以 therapist 开头>` 后门只在 `DEV_LOGIN=1` 时生效。
