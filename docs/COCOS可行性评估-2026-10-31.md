# Cocos 引擎可行性评估 —— 接水果 / 康复训练小程序

> 评估对象：把接水果（或五个体感游戏）迁移到 Cocos Creator。
> 依据：`engine-feasibility.md` 三档结论格式。**结论只针对「Cocos Creator 3.8.x + 微信平台 + 现有项目形态」，引擎版本或平台变了要重新核对。**
> 日期：2026-10-31

---

## 一、结论总表

| # | 需求 | 结论 | 依据 | 替代方案 |
|---|---|---|---|---|
| 1 | 在**现有小程序的 tabBar / 分包页面里**跑 Cocos 游戏 | ❌ **建议换方案** | Cocos Creator 的构建产物是 **微信小游戏**（`game.json`），官方明确：小程序只能用微信官方框架开发，第三方引擎只能打包成小游戏（来源：Cocos 官方文档 publish-wechatgame、Cocos 论坛 #58556） | 见「路线 C」 |
| 2 | 把接水果单独做成 **Cocos 微信小游戏** | ⚠️ **要改造** | 技术上能做（小游戏首包 4MB、支持 wx BLE API），但需要**游戏类目资质**（与现在的健康类小程序 appid 不同类型）、独立立项、BLE→指标→上报全链路重接 | 见「路线 B」 |
| 3 | 用 web-view 把 Cocos H5 嵌进小程序页面 | ❌ **建议换方案** | web-view 只能加载 H5；游戏需要 **wx BLE 姿态数据**（`utils/motion.js`），H5 里拿不到小程序蓝牙，只能 postMessage 桥接——高频姿态数据（30Hz+）经桥接会丢帧、断流，判定精度直接受损 | 路线 A |
| 4 | 继续用现有自研 canvas 引擎增强 | ✅ **能做** | v3 已交付（黄金果/果子雨/天空时段），判定、指标、可复现序列全部保全 | — |

## 二、为什么「在现有小程序里跑 Cocos」不成立（关键事实）

1. **两种应用类型**。本项目 `app.json` 有 `pages` / `tabBar`——是**微信小程序**（WXML 页面框架）。Cocos Creator 构建面板只有「微信小游戏」目标，产物是 `game.json` + 开放数据域，**没有页面概念，没有 tabBar，不能作为分包嵌进小程序**。微信论坛引擎方回复原话：「小程序只能用微信官方提供的框架开发」。

2. **类目与资质**。小游戏必须挂**游戏类目** appid。本项目的 appid（`wx345984238e3c0176`）是健康类小程序；医疗健康 + 游戏类目的审核材料、主体要求完全不同，不是改个配置的事。

3. **全链路耦合**。接水果的可复现训练依赖这条链：
   `BLE(WT9011DCL) → utils/witble → utils/motion（零点/死区/低通）→ engine（reachDeg 自适应、逐颗 trk 留痕）→ metrics v2（够得着/反应/到位/稳定率）→ 训练记录 → 治疗师看板`。
   Cocos 版要么把这条链整个搬进小游戏重接，要么丢掉指标——丢掉指标就不是康复训练工具了。

4. **五个游戏一个底座**。pkgShoot/pkgRace/pkgWire/pkgRhythm/pkgFruit 共享 `utils/scene/depth.js`、motion、记录体系。接水果迁走，其余四个留在原地，两套引擎两套指标口径，治疗师数据没法比。

## 三、三条路线

### 路线 A：继续现有引擎（推荐）
- **现状**：v3 已交付——黄金苹果、果子雨、连击光环、天空时段推移，全部矢量代码，判定与指标零改动。
- **后续增强空间**（同引擎内，成本从低到高）：更多 juice（连击里程碑全屏演出、果子入篮堆叠感）、场景事件（蝴蝶/风）、治疗师可选的干扰项开关。
- **成本**：增量开发，无迁移风险。

### 路线 B：独立 Cocos 小游戏（新产品线）
- **做法**：新申请游戏类目 appid → Cocos Creator 3.8 建工程 → 重写接水果 → 通过 BLE API 重接传感器 → 指标与上报重新实现 → 小程序里用「跳转小游戏」入口衔接。
- **能做，但要新立项**：游戏类目资质、独立审核、BLE 链路重写、指标口径重新验证、服务器托管远程资源（小游戏超出首包的资源必须走远程服务器——目前唯一服务器是家网 1~5Mbps，**备案域名还没批**，这是当前的阻塞项）。
- **工作量级别**：整个产品级新项目，不是"移植"。收益是 Cocos 编辑器化的迭代效率与更重的表现力，**但核心玩法（倾身移动果篮接水果）一个 2D 场景 + 一个 UIBlock 就能做，Cocos 的引擎优势用不上多少**。

### 路线 C：借鉴 Cocos 的架构思想，不换引擎
- 把 `renderer.js`（2448 行）按 Cocos 的组件模型拆成「节点-组件」结构（背景层/实体层/特效层/HUD 层各自独立、生命周期统一），渲染入口标准化。
- 收益：后续给五个游戏加内容时结构更清晰；成本：纯重构，无新能力。

## 四、性能预算对照（假设走了路线 B，供参考）

| 设计项 | Cocos 侧 | 结论 |
|---|---|---|
| 接水果同屏 ≤3 果 + 果篮 + 粒子 | 远低于「数百节点」警戒线 | ✅ 无风险 |
| BLE 姿态 30Hz → 引擎输入 | 小游戏支持 wx BLE | ⚠️ 需实测延迟与丢帧（真机 + 低端安卓） |
| 指标逐颗留痕 | 纯逻辑，可移植 | ✅ 但口径要重新验证 |
| 首包 + 远程资源 | 资源必须上远程服务器 | ❌ 当前卡在备案域名未批 |

## 五、建议

**短期（本轮已交付）**：路线 A。v3 的玩法与表现提升是真实的，且保住了可复现训练与指标口径。

**如果 Cocos 的诉求来自"想要 Cocos 那种画面质感"**：那不是引擎问题——v3 的瓶颈不在渲染技术（矢量绘制可以继续加细节），在美术资产。先用预览工具确认想要什么风格，再决定是否值得为它开路线 B。

**如果诉求是"团队后续要转 Cocos 生态"**：那是路线 B 的立项讨论，先解决游戏类目资质与远程资源服务器两件事再动工。
