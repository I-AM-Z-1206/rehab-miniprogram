# 左右节奏训练 · 体感康复小游戏（rhythm）

WT9011 **卡在胸带上**（胸带从**腋下最高点**绕一圈固定），标定中立位后，身体左右偏移 → 归一化控制量 `nx ∈ [-1,1]` →
判定当前处于**左 / 中 / 右**哪个区域（三车道：中向音符要求「回到中立位」）。音符按 BPM 精确生成，
玩家在音符到达判定线时把身体保持在正确一侧即为命中；方向和时间各算一项指标。

## 2. 状态机

```
IDLE(intro) ─start→ READY(prepare) ─calibrate→ CALIBRATING
                       │                          │
                       └─────enter──────▶ COUNTDOWN（预备拍 4 拍）
                                                 │ 音乐开始
                                                 ▼
                            PAUSED ◀──pause──▶ PLAYING ──timeout/quit──▶ RESULT / ABORTED
                                                 │
                                    SENSOR_ERROR ◀─断线/超时
                                        │
                                        └─resume（数据恢复）→ PLAYING
```

* 只有 `PLAYING` 会推进音乐时间与判定；`PAUSED` / `SENSOR_ERROR` / `RESULT` 全部冻结。
* `finish()` 只结算一次（`settled`），重复调用不会重复加分。
* 断线**不会**自动切模拟，也不会把漏掉的音符判成命中。

## 3. 时间基准与音画同步

* 主时钟：`performance.now()`（单调递增），**不用帧数累加**。
* 音频 `currentTime` 只用于纠偏：偏差 > 80ms 硬纠正，否则按 5% 软拉。
* 音频 `loop` 播放时 `currentTime` 回绕，用回绕检测累计 `loopCount`，
  得到连续音乐时间；循环长度 = 整数小节，因此不会累积漂移。
* 暂停：记录 `pausedAt`，恢复时重设锚点，音频从暂停点继续。
* 判定时间 = `音乐时间 − syncOffsetMs`；视觉位置用音乐时间。
  `syncOffsetMs > 0` 表示"听到比看到晚"，在准备页用「试听 8 拍」校准。
* 音频不可用 → `silent` 模式：时钟照跑，界面显示「无音乐」，**不声称与音乐同步**。

## 4. 谱面

```js
{ noteId, targetSide: 'left'|'right', beatIndex, targetTimeMs, noteType, scoreValue }
```

* `targetTimeMs = offsetMs + beatIndex × (60000 / BPM)`，单位毫秒。
* 生成规则（`buildChart`）：从第 `prepBeats` 拍开始，每 `noteStepBeats` 拍一个音符；
  左右交替为底版，按 `centerRate` 概率换成中向音符（要求回到中立位），
  按 `sameSideRate` 概率出现同向连续；小节第一拍标为 `accent`（分值 120）。
  `centerRate = 0` 时退化为纯左右两车道。
* **呼吸拍是固定间隔，不是随机**：`restRate` 表示"每 N 个音符空一拍"
  （`N = round(1 / restRate)`，最小 4）。这样间隔只可能是「1 个步长」或「2 个步长」，
  不会出现"连着空两三拍 → 一堆音符之后半天没一个"的手感。
* **同向连续必须间隔 ≥ `sameSideGapMs`**，否则生成时强制换向 —— 否则在"一次动作只结算一个音符"的规则下玩家根本打不出来。
* 同曲 + 同难度 + 同种子 + 同算法版本 → 完全相同的音符时间表（训练可对比）。
* `parseChart()` 可读取外部 JSON，逐条校验方向/时间/ID 重复，不合法只报错不静默丢弃。

## 5. 身体输入

复用 `utils/motion.js`（死区 → 归一化 → 一阶低通 → 方向滞回），只消费：

* `nx ∈ [-1,1]`：归一化控制量（不是厘米位移）
* `dir`：`left` / `center` / `right`，阈值由 `sideThreshold` 决定
* `stale`：> 1.2 秒没有新帧 → 立即进入 `SENSOR_ERROR`

游戏再叠一层"动作事件"：

* `enterAt`：这一侧是什么时候进入的（用于算节奏误差）
* `stableMs`：进入后保持多久（`stableMs` 之前不算命中，过滤路过抖动）
* `actionSeq`：进入动作的序号；**一次动作最多结算一个音符**
  例外：保持同一侧时，距上次命中 ≥ `sameSideGapMs` 可再次命中（避免"一直站着刷分"）

## 6. 判定规则（hit-judge.js）

```
音符到达判定线（targetTime）之前：一律不判 —— 提前站好不算准
到达之后：
  · 方向错误且已稳定      → MISS（记 wrongDirection，同时断连击）
    （中向音符例外：回中路上必然经过两侧，给满整个窗口再判方向错误，
     窗口内回到中间按迟到正常判，避免误伤正在正确移动的患者）
  · 方向正确 + 稳定 + 动作可用：
        时间误差 = 进入该侧的时刻 − 目标时刻（提前站好最多算到窗口边缘）
        |误差| ≤ perfectMs → PERFECT
        |误差| ≤ greatMs   → GREAT
        |误差| ≤ goodMs    → GOOD
  · 超过 goodMs 仍未就位  → MISS（late / no-input / no-new-action）
```

判定窗口全部可配（`perfectMs < greatMs < goodMs`，校验会拦截顺序错误），
颜色、英文名、中文名、图形标记四者同时呈现，不只靠颜色区分。

## 7. 计分

```
单音符得分 = 音符分值 × 连击倍率
连击倍率   = min(comboMaxMul, 1 + max(0, combo-1) × comboStep)
总分       = 基础分合计 + 连击加成合计 + 完成奖励

节奏准确率 = (PERFECT×1 + GREAT×0.7 + GOOD×0.4 + MISS×0) / 已判定数
方向准确率 = 命中数 / (命中数 + 方向错误数)
综合命中率 = 命中数 / 谱面音符总数
```

分母为 0 一律返回 `null`，界面显示「暂无数据」（不会冒充 100%）。

## 8. 难度与配置

默认节奏：66 BPM、**每拍一个音符**（约 0.9 秒来一个）、休止拍 12%、预备拍 2，
飞行时间 2.6 秒 —— 音符看着长、来得连贯，不会"半天才来一个"，也不会快到反应不过来。
1~5 档预设只覆盖手感参数（音符间隔 2 / 1.5 / 1 / 0.75 / 0.5 拍、休止比例、判定窗口、
飞行时间、时长、预备拍），体感输入与曲目选择保持治疗师设置。可调项：

* 音乐：曲目（静水深流 66 / 晨光漫步 90 / 心跳律动 110 BPM）、音量、音画补偿、节拍脉冲、节拍点击音
* 训练目标：时长、预备拍
* 体感输入：左右轴、反向、灵敏度、死区、跟手度、左右边界
* 左右判定：区域阈值、稳定判定时间、同向重复间隔
* 节奏判定：三档窗口、飞行时间、音符间隔、中间音符比例、休止比例、同向比例、谱面种子
* 计分：三档分值、连击步长/上限、漏接是否断连击、完成奖励
* 反馈：音效、语音、振动、引导提示

## 11. 性能与异常

* 静态背景（夜空 + 极光 + 暗角 + 三色车道 + 网格）离屏缓存，每帧只 `drawImage` 一次；`drawImage` 必须显式给目标宽高。
* 每帧新增的动态层控制在低开销范围：12 条车道流光（描边）、判定线柔光（1 个渐变）、
  每个音符 3 节拖尾菱形 + 1 个外圈描边、3 块地台底光（3 个径向渐变）。
* 高频传感器数据只写进 `MotionTracker`，页面**没有任何逐帧 setData**。
* 音符按时间游标加入 `active`，判定后保留 700ms 淡出再回收，并有上限保护。
* 页面隐藏：停帧循环 + 暂停音乐 + 停语音；卸载：结算落记录、销毁音频、断开共享蓝牙。

### 真机验收步骤

1. 连接 WT9011（50Hz）→ 准备页显示「传感器已连接 / Hz」。
2. 中立位 3 秒完成标定 → 点「试听 8 拍」调音画补偿，让闪烁与听到的拍子重合。
3. 开始 → 先听 4 拍预备，音乐开始后按拍左右移动；音符到判定线时保持在正确一侧。
4. 暂停：音乐、音符、判定、计时全部停住；恢复后不跳帧、不重复计分。
5. 关掉传感器：进入「传感器数据中断」，不判定、不加分；重连后可继续，结算里带中断时长。
6. 结算：分项之和 = 总分；三个准确率公式与记录页一致；无样本显示「暂无数据」。

## 13. 待真机确认

* **轴向与正负**：默认 `axisX = pitch`、`invertX = true`，换佩戴方向可能要改（设置页可改，立即生效）。
* **音画同步**：不同机型/蓝牙耳机延迟不同，必须用「试听 8 拍」现场校准；补偿值会写进记录。
* **判定手感**：`sideThreshold`（0.35）、`stableMs`（120ms）、`goodMs`（160ms）是按 90/110 BPM 估的初值，需按患者能力微调。
* **同向连击间隔**（320ms）：若患者保持一侧的稳定性差，可上调该值减少"来不及重新进入"的漏接。
* **音轨格式**：打包用的是 **22.05kHz 单声道 AAC（.m4a）**，三首合计约 300KB（静水深流 66 / 晨光漫步 90 / 心跳律动 110 BPM）；wav 是同参数中间产物，循环边界零跳变，只用于转码、不进包。
  转码命令写在 `tools/gen_rhythm_audio.py` 头部；若某机型循环有缝，先在真机确认再考虑换编码与重新校正循环长度。
* **上报接口**：需在设置页填 https 地址与令牌；隐私清单与同意流程已就位。

界面走「奶油白 + 糖果色」，不用霓虹/发光：

* 背景：浅天蓝 → 奶油白渐变，太阳、圆角云朵、远景丘陵与小树、飘落花瓣、空中光斑；
* 跑道：奶油路面 + 三色车道，路缘彩色描边 + 白色内线，路面两侧有柔和外投影；
  每一拍一条横向节拍线顺路流向判定线；
* 跑道：奶白色路面，三条车道分别染草莓粉 / 蜂蜜黄 / 薄荷绿，白色圆头虚线分道；

  方向用「双雪佛龙」而不是实心三角（实心三角会被读成播放键），中间音符用白点标记；

* 判定地台：白色胶囊 + 糖果色描边 + 软阴影，选了哪侧就轻轻抬起；
* 玩家：白色小团子（眼睛 + 腮红 + 微笑），在三个刻度之间移动；
* 文字：深蓝灰 `#3F4A5A` 白底可读；判定字用深色版配色（`VERDICT_INK`）+ 白描边。

配色集中在 `games/rhythm/renderer.js` 顶部的 `C`，改主题只改这一个对象。

## 15. 节奏跟不上 / 断断续续 / 音符堆积（2026-10-30 修正）

实际试玩反馈：「左右变化太快，我自己都跟不上」「音符一下好多、一下没有」「音符停留有问题」。
三条都能落到具体数字上，不是手感-tuning 能解决的。

### 15.1 根因：难度是按拍数定义的，BPM 一变难度就漂移

`noteStepBeats` 是**拍数**（相对量）。同一个「标准」档：

| 曲目 | BPM | 难度 3 的实际间隔 |
| --- | --- | --- |
| 静水深流 | 66 | 909 ms |
| 晨光漫步 | 90 | 666 ms |
| 心跳律动 | 110 | **545 ms** |

治疗师选同一档难度，换个曲子速度差 1.7 倍。而康复患者完成一次左右转移再稳定下来
大约需要 700ms 以上 —— **545ms 的间隔在数学上就不可能命中**，患者只能一路漏接。

改法：新增 `minGapMs`，谱面生成时以**毫秒**为目标，从合法拍值
`[0.5, 0.75, 1, 1.25, 1.5, 2, 2.5, 3, 4]` 里挑换算后最接近的那个。
音符仍然落在拍点上（音乐性不丢），但绝对间隔进入安全区。
另设 620ms 硬下限兜底。

> 先试过「不够就整倍数放大」，粒度太粗：66 BPM 的 909ms 会被直接翻到 1818ms，
> 明明只差 9% 却慢了一倍。

修正后难度 3：909 / 1000 / 1090 ms（漂移 1.67× → 1.20×）；难度 5：666~681 ms（1.02×）。

### 15.2 根因：判定在惩罚「提前移动」

时间误差 = 进入该侧的时刻 − 拍点，而 early 和 late 用**同一个**窗口。

但躯干不是按键 —— 它必须**提前启动**才能准时到位，移动本身就要几百毫秒。
所以「早于拍点进入」是唯一的、正确的策略，不是失误。
原逻辑下患者做对了（提前启动、准时到位）却被判 MISS。

改法：新增 `earlyFactor`（默认 1.8），**只放宽 early 一侧**，late 保持严格
（那才是真的跟丢了节奏）：

| 提前量 | 改前 | 改后 |
| --- | --- | --- |
| 150 ms | GOOD | PERFECT |
| 250 ms | **MISS** | GREAT |
| 350 ms | **MISS** | GOOD |
| 450 ms | MISS | MISS |

迟到侧不变：迟到 250ms 改前改后都是 MISS。

### 15.3 根因：休止拍让间隔突然翻倍

原来「每 N 个音符空一拍」，空的位置落在小节中间，效果是间隔从 666ms 跳到 1333ms
—— 患者刚建立起来的节奏预期被整段打断，主观感受就是「一下子好多、一下子又没有」。

改法：休止**只在小节末尾**留空（用 `floor(b/bar)` 判断跨小节，不用浮点取模 ——
step 是 0.75 这类值时 `(b+step) % beatsPerBar` 永远不会正好落在 0 上，休止就再也不触发了），
并按小节计数。同时把各档 `restRate` 下调（0.28/0.2/0.12/0.08/0.06 → 0.2/0.14/0.08/0.06/0.04），
减半休止次数。

### 15.4 根因：停留时间比音符间隔还长

`NOTE_TAIL_MS = 700`，而标准档音符间隔只有 666ms —— 下一个音符都到了，
上一个还堆在判定线上，患者看不出该看哪一个。

改法：降到 380ms；并且让过了线的音符**继续往前走一小段**再淡出，而不是停在判定线上
（`_noteY` 里 `p > 1` 时继续下移 30%）。停住的话密集谱面上判定线附近会糊成一团。

### 15.5 顺带修掉的偏侧 bug

`chart.js` 的交替逻辑 `lastSide === 'left' ? 'right' : 'left'` ——
当 `lastSide === 'center'` 时走 else 分支，**恒取 left**。
所以每个中间音符之后必然是左侧音符，实测左比右多 14~32%，康复训练最忌讳左右不对称。

改法：交替基于**上一个非中间音符**（`lastNonCenter`）判断。修正后左右差 ±4 以内。

### 15.6 五档难度的新参数

每档都带 `minGapMs`（毫秒下限），判定窗口整体放宽：

| 档 | minGapMs | perfect/great/good | restRate |
| --- | --- | --- | --- |
| 1 入门 | 1600 | 110 / 180 / 260 | 0.20 |
| 2 轻量 | 1250 | 95 / 160 / 235 | 0.14 |
| 3 标准 | 1000 | 85 / 145 / 210 | 0.08 |
| 4 进阶 | 820 | 75 / 128 / 190 | 0.06 |
| 5 挑战 | 680 | 65 / 112 / 170 | 0.04 |

`chartSeedVersion` 从 `v2` 升到 `v3`：谱面生成算法变了，旧种子会重新生成，
同一患者的训练记录**不与改版前直接可比**，做前后对比时要注意。

## 16. 音符节奏与音乐解耦（2026-10-30 定版）

**结论：音符不再跟着音乐拍点走，节奏由毫秒直接给定。**

### 16.1 为什么要解耦

上一轮（第 15 节）用「毫秒下限 + 吸附到最近拍值」把漂移从 1.67 倍压到 1.20 倍，
但**只要音符必须落在拍点上，BPM 就仍在决定训练强度**：

| 档位 | 66 BPM | 90 BPM | 110 BPM |
| --- | --- | --- | --- |
| 标准（旧） | 909ms | 1000ms | 1090ms |

三档看着接近，是因为它们都被迫从 `[0.5, 0.75, 1, 1.25, 1.5, 2, 2.5, 3, 4]` 里挑
——**能取的值本来就被拍值离散化了**，想给 1150ms 只能取 1000 或 1250。
治疗师其实根本不打算让音乐参与难度决策，是 BPM 自己挤进来的。

康复训练里音乐是背景，不是考官。患者该多久动一次，取决于他完成一次重心转移
需要多久，跟这首曲子多少 BPM 没有任何关系。

### 16.2 改法

`buildChart()` 拆成两步，**两种模式只差第一步**：

1. **算时间点**
   - 自由模式（默认）：`t = prepMs`，然后 `t += gapMs` 直接推进，与 BPM 无关；
   - 吸附模式（`snapToBeat`）：从合法拍值里挑换算后最接近 `noteGapMs` 的，音符仍在拍点上。
2. **分配方向**：左右交替 / 中间音符 / 同向连续 —— 两种模式共用同一套规则。

新增参数：

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `noteGapMs` | 1100 | **训练强度的主参数**，两个音符之间隔多少毫秒 |
| `snapToBeat` | false | 打开才吸附拍点；关闭时严格按毫秒走 |
| `prepMs` | 2400 | 开头留白，建议 ≥ 音符飞行时间，否则第一个音符会「半路冒出来」 |

`noteStepBeats` 保留，但**只在 `snapToBeat` 打开时生效**。
`minGapMs` 退役（语义从「下限」变成「目标间隔」，已并入 `noteGapMs`）。

### 16.3 呼吸改成「拉长间隔」，不再「跳过音符」

原来休止是跳过一个音符，间隔直接翻倍（666 → 1333ms）。患者刚建立起来的节奏
预期被整段打断，主观感受就是「一下子好多、一下子又没有」——这是用户原话。

改成把间隔拉长到 **1.5 倍**（`BREATHE_FACTOR`）：音符一个不少，只是慢半拍，
节奏不断线。合法间隔从此只有两种值：`gapMs` 与 `gapMs × 1.5`。

### 16.4 物理下限 620ms

`HARD_MIN_GAP_MS = 620` 兜底：低于这个值，多数患者一次左右转移都做不完，
只能一路漏接。即使治疗师把 `noteGapMs` 拉到 400，实际也不会低于 620。

### 16.5 视觉提示必须跟着音符，不能跟着拍点

这是解耦后最容易漏的一处。判定线 / 踏板 / 光柱的呼吸原本用 `clock.beatPhase()`
驱动，解耦后会出现「灯在拍点上闪、音符在别的时候到」，患者照着灯动反而全错。

新增 `engine._notePhase()`（0 = 下一个音符还很远，1 = 马上到），三处呼吸全部改用它。
顺带把按钮文案「节拍开/关」改成「提示开/关」——它提示的是音符，不是节拍。

`beatClickOn`（拍点点击音）默认改为关闭：它按音乐拍点响，与「该动了」的时刻无关。

### 16.6 五档预设（毫秒）

`noteGapMs` 按「一次重心转移要多久」定，不按拍数定：
患者完成一次左右转移 + 稳定判定约需 700~900ms，所以入门档留两倍余量，
挑战档才压到 780ms。

| 档 | noteGapMs | perfect/great/good | prepMs / approachMs | restRate |
| --- | --- | --- | --- | --- |
| 1 入门 | 1800 | 110 / 180 / 260 | 3000 / 3000 | 0.20 |
| 2 轻量 | 1450 | 95 / 160 / 235 | 2800 / 2800 | 0.14 |
| 3 标准 | 1150 | 85 / 145 / 210 | 2600 / 2600 | 0.08 |
| 4 进阶 | 950 | 75 / 128 / 190 | 2400 / 2400 | 0.06 |
| 5 挑战 | 780 | 65 / 112 / 170 | 2200 / 2200 | 0.04 |

### 16.7 验证：患者模型跑完整一局

新增 `tools/rhythm-playability-test.js`（29 项）：模拟患者只会提前启动 + 0.35s
缓动移动，跑完整一局。结果：

| 难度 | 66 / 90 / 110 BPM 音符数 | 提前 250ms | 提前 400ms |
| --- | --- | --- | --- |
| 1 入门 | 42 / 42 / 42 | 100% 命中 | 100% 命中 |
| 3 标准 | 71 / 71 / 71 | 100% 命中 | 100% 命中 |
| 5 挑战 | 106 / 106 / 106 | 100% 命中 | 100% 命中 |

**三首曲子音符数完全一致** —— 换曲子不再改变训练强度，这是本次的核心指标。
判定仍有区分度：提前 250ms 时难度 5 只有 15~21 个 PERFECT（其余 GREAT/GOOD），
提前 400ms 则全掉到 GOOD，不是无条件满分。

### 16.8 影响

- `chartSeedVersion` 从 `v3` 升到 `v4`：谱面算法变了，
  **改版前后的记录不可直接对比**。
- 治疗师设置页的「音符间隔」单位从「拍」变成「毫秒」，预设对比表同步改。
- 吸附模式保留给「想让动作跟音乐走」的场景，代价是换曲子难度又会漂移
  （测试里有对应断言把这个代价钉住）。

## 17. 判定有效性：接上失效的阈值，堵住站桩后门（2026-10-30 17:00）

前两轮诊断出两个影响训练有效性的缺陷，本轮修掉。

### 17.1 `sideThreshold` 从来没生效过

`utils/motion.js` 里方向判定写死 ±0.1：

```js
if (this.nx < -0.1) this.dir = 'left'
else if (this.nx > 0.1) this.dir = 'right'
```

而配置项 `sideThreshold` 的默认值是 **0.35**。它在全项目只出现一处：
`engine.js` 把值**写进记录的 `controlConfig`**。

于是造成两件事：

1. 治疗师拖滑块**毫无效果**；
2. 失效的 0.35 被写进训练记录 —— 事后分析会以为阈值是 0.35，
   实际判定用的是 0.1。**实际阈值比设定小 3.5 倍**，患者轻轻一动就算「进入该侧」。

**改法**：`motion.js` 改读配置，缺省 0.1（等于旧硬编码值，其它四个游戏不受影响，
它们的配置里没有这个键）。

**顺带要改默认值 0.35 → 0.2。** 0.35 既然从未生效过，直接接上等于暗改判定：
患者「进入该侧」的时刻整体推迟约 120ms，实测难度 5 的 PERFECT 直接归零。
按默认死区 1.5° / 边界 12° 换算：

| 阈值 | 对应侧倾 | 评价 |
| --- | --- | --- |
| 0.10 | 2.7° | 太浅，呼吸抖动都能触发（旧的实际值） |
| **0.20** | **3.9°** | 死区的 2.6 倍，明确侧倾才触发 ← 取这个 |
| 0.35 | 5.7° | 要明显摆动，幅度小的患者进不去 |

### 17.2 站桩后门

```js
_actionOk(note, now) {
  if (this.action.seq > this.action.consumedSeq) return true   // 有新动作
  return now - this.action.lastHitAt[note.targetSide] >= sameGap  // ← 后门
}
```

第一行是对的。第二行无条件放行：没有新动作时，只要距上次同侧命中 ≥ 320ms 就过。
而交替谱面下同侧音符间隔是 **2 个音符**（约 2.3 秒），远大于 320ms ——
**后门永远开着**。实测难度 3 站着不动能拿 42% 命中（全是 GOOD）。

注释里写着「否则玩家只要一直站在左侧，所有左侧音符都会自动命中」——防的就是这个，
但防错了地方：它防的是「不移动」，而真正漏掉的是「不需要移动的音符」和「需要移动的音符」
没有区分开。

**改法**：谱面在生成时标记 `repeat`（这条跟上一条同侧且非中间），
只有 repeat 音符才允许走后门（同向连续，患者已经在正确位置，不需要重新进入）。

```js
if (note.repeat) return now - lastHitAt[side] >= sameGap   // 同向连续
if (note.targetSide === 'center') return now - lastHitAt.center >= sameGap  // 回中
return false                                                // 需要换侧却没动 → 不中
```

中间音符保留放行：回中不产生新的 seq（`_updateActions` 只在进入左/右时自增），
只能走这条；而且「保持在正中」本身就是有效训练，站着不动满足它是正确的。

### 17.3 效果

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 站桩命中率（难度 3） | 42% | **28%**（= centerRate 0.3） |
| 站桩时左右音符命中数 | 49 | **0** |
| 记录里的 sideThreshold | 写了 0.35，实际 0.1 | 写 0.2，实际 0.2 |
| 正常患者命中率 | 100% | 100%（未受影响） |

### 17.4 记录版本

新增 `judgeVersion: 'v2'`：

- `v1` = 阈值未接线 + 无条件后门
- `v2` = 阈值接配置 + 后门只对同向连续开放

**v1 与 v2 的命中率不可直接对比。** 谱面（`chartSeedVersion`）没变，
变的是「怎么算命中」。

### 17.5 新增断言

- `rhythm-headless-test` [11]（5 项）：同一控制量 0.5 在阈值 0.2 下判 right、
  在 0.6 下判 center —— 滑块必须真的改变判定结果。
- `rhythm-playability-test` [4]（6 项）：三个难度下站桩时左右音符命中数必须为 0、
  总命中率 < 45%。

## 18. 放慢：飞行速度、间隔、以及一条漏网的节拍线（2026-10-30 17:20）

用户反馈「音符来的速度太快」。拆开看是三个独立的东西叠在一起。

### 18.1 三处一起改

**① 飞行缓动是「加速」的**（`_noteY`）

`Math.pow(p, 1.15)` —— 指数大于 1 意味着**末尾加速**：同样 20% 的时间，
最后一段走完了 25% 的距离。越接近判定线冲得越快，主观就是「扑过来」。
曾经从 1.7 降到 1.15，但那只是把冲刺削弱一点，**方向没变**。
改成匀速（指数 1.0）—— 匀速是唯一能预判的曲线，患者才练得出稳定的提前量。

横向 `_laneX` 和放大 `scale` 同步改线性：三条曲线不一致时，
音符会走成一条弧，看起来像「飘」而不是「落」；放大的 `p^1.2` 也会
在临近判定线时加速膨胀，和纵向冲刺叠在一起。

**② 五个档的 `approachMs` 全部加长**

飞行距离固定在约 245px（地平线 0.12h → 判定线 0.84h，在 340px 高的舞台上），
所以它直接决定视觉速度：

| 档 | approachMs | 视觉速度 | 屏上同时 |
| --- | --- | --- | --- |
| 入门 | 3800（原 3000） | 64 px/s | 1.73 |
| 轻量 | 3600（原 2800） | 68 px/s | 2.00 |
| 标准 | 3400（原 2600） | 72 px/s | 2.34 |
| 进阶 | 3100（原 2400） | 79 px/s | 2.70 |
| 挑战 | 2800（原 2200） | 87 px/s | 3.11 |

**③ 五个档的 `noteGapMs` 也放宽一档**（用户说的「来」更可能指频率）

| 档 | noteGapMs | 一局音符（90s） |
| --- | --- | --- |
| 入门 | 2200（原 1800） | 约 38 |
| 轻量 | 1800（原 1450） | 约 47 |
| 标准 | 1450（原 1150） | 约 56 |
| 进阶 | 1150（原 950） | 约 71 |
| 挑战 | 900（原 780） | 约 90 |

两个参数**同步放宽**的好处是屏上音符数几乎不变（2.26 → 2.34 个），
但每个音符更慢、更稀 —— 不会变成「一堆慢音符挤在一起」。

### 18.2 一条漏网的节拍线

`_drawBeatLines` 按**音乐拍点**画横线流向判定线。第 16 节把音符和拍点解耦之后，
这条线就成了纯干扰：横线按 66 BPM 流过来，音符按毫秒来，两者抵达判定线的
时刻对不上。患者会拿横线当「该动了」的信号，然后每次都错；而且画面被两套
不同频率的节奏填满，主观感受就是「又密又快」。

改：只在 `snapToBeat` 打开时绘制（那时音符真的落在拍点上）。

**这是解耦漏掉的第二处**（第一处是判定线/踏板/光柱的呼吸）。
教训：**解耦时要把「按拍点驱动的视觉元素」全找一遍，不能只改明显的那几个。**

### 18.3 倒计时跟着收短

`countdownMs = prepMs × 0.6`。飞行时间加长到 3800ms 后，0.6 会让开局空等
6 秒（倒计时 2.3s + 飞行 3.8s），患者会以为卡住了。系数降到 0.4，
上限从 2400 收到 2000 —— 倒计时只负责「准备好」，不该抢走飞行时间。

### 18.4 预览工具的构建

`npm run preview:rhythm` 原来是 esbuild 直写 `tools/rhythm-preview/bundle.js`，
在这个项目里会被拦（Access is denied，和 `tools/shoot-preview` 同一个坑）。
改为 `node tools/rhythm-preview/build.js`（`write:false` + Node 落盘）。

`tools/fruit-preview` / `tools/wire-preview` / `tools/shoot-preview` 的
npm script 仍是直写版本，**用之前先按同样方式改**。

## 19. 视觉重做：清晨逆光跑道（2026-11-01）

用户反馈：「不好玩、没有吸引力、画面不行」。原「奶油白 + 糖果色」那一版（第 13.5 节）
整套废弃。**engine / chart / score / hit-judge / beat-clock 一行未动**，只改 `renderer.js`。

### 19.1 为什么原版「平」

| 现象 | 量化 |
| --- | --- |
| 没有暗部 | 全画面最深只到 `#3F4A5A` 且只用于文字，其余 90% 面积在 70% 亮度以上 |
| 容器化到底 | 4 张统计卡 + 曲目卡 + 音符卡 + 连击牌 + 身体位置面板 + 4 个胶囊 = 12 个容器 |
| 跑道是塑料滑梯 | 三色锥形渐变 + 硬直边线，没有雾、没有纵深、没有材质 |
| 和音乐无关 | 山 / 樱花 / 太阳全是静态贴纸，66 BPM 只驱动了音符 |
| 命中反馈为零 | 音符直接消失 + 一个白胶囊飘字 |

更关键的一条：**高明度底色撑不起任何辉光**。光效画在浅色上会被直接洗没，
所以「加特效」这条路在糖果底色上是走不通的，必须先换基调。

### 19.2 定下来的五件事（用户逐条选的）

1. 基调：**清晨逆光跑道**，与走钢丝同一世界观；
2. 容器：**全拆**，只留暂停面板与结算页；
3. 命中反馈：**克制但明确** —— 炸点 + 判定线光晕 + 每 5 连击光柱升阶 + 完美时地平线亮一下，
   **不做屏幕震动、不做闪白**；
4. 背景：**只呼吸**（地平线金光随拍 ±8%），不做整片起伏；
5. 范围：介绍页 / 准备页 / 对局 / 结算**四个界面全改**；音符改**逆光光球**。

第 3、4 条是康复约束，不是审美偏好：
屏幕震动会干扰患者靠视觉判断身体位置；背景整片起伏会被误读成「自己没站稳」。

### 19.3 逆光配色的三条硬约束（沿用走钢丝那套）

1. **金色只允许出现在地平线最后 8%**。给到 24% 就成「渐变壁纸」。
2. **远山必须是比天空暗的剪影**，越近越暗。三层都比天空亮 = 三张半透明纸。
3. **云体必须冷白**（236,242,250）。整朵米黄 + 上亮下暗 = 沙丘。

另外三条本文件特有的：

* **地面渐变第一档必须贴着天空最底部的暖色**，否则天地之间有一条硬边（比加任何雾都管用）。
* **太阳本体必须画在跑道与远端雾之后**。放在天空层里会被跑道收口和雾盖成一团白，
  画面上就没有光源了 —— 逆光的全部依据是「看得见光源」。
* **任何雾都不能用 fillRect 铺矩形**，径向/线性渐变必须收到 0 alpha，否则两侧切出方块。

### 19.4 车道语言：从糖果色改成色温

糖果色（粉/黄/绿）在暗底上会浊成泥，还会和地平线的暖金抢注意力。现在统一成：

| 车道 | 色 | 理由 |
| --- | --- | --- |
| 左 | 冷青 `rgba(150,212,246,…)` | 冷↔暖是患者不需要学就能读懂的左右区分 |
| 中 | 暖白 `rgba(255,238,200,…)` | 中性 |
| 右 | 琥珀 `rgba(255,196,132,…)` | |

同一套语言贯穿音符光球、判定台边缘、身体位置轨道、命中碎光。判定线是**唯一的冷白主线**，
因为地平线已经占了暖金，同色温会糊在一起。

### 19.5 新增的四个效果（借 pixelfx 的方法，不借像素）

| 效果 | 做法 | 为什么是这个 |
| --- | --- | --- |
| 命中冲击帧 | 0.34 内一个近白亮核配合扩散环 + 10 颗 easeOut 碎光 | 只画扩散环没有重量，必须先「炸」一下 |
| 连击光柱 | 每 5 连击升一阶，沿跑道两侧往上长，越亮越宽 | 「积累感」的唯一载体，不靠震动和闪白 |
| 地平线脉冲 | perfect / great 时整条地平线亮一下（620ms 衰减） | 全画面唯一的整屏级回应，所以只给最高判定 |
| 跑道流光 | 3 条极淡光带沿跑道缓慢流过（周期 5s+） | 解决「跑道是一块静止的深色梯形」，快了会诱发追视 |

碎光、光尘都不用 `Math.random`（沿用 fx.js 的确定性契约，`hash()` 取值）。

### 19.6 拆容器时踩的坑

* **改文字色必须同时改底色**。`C.ink` 从深蓝灰改成暖白后，`_button` 的默认底色还是
  `rgba(255,255,255,0.92)`，准备页那几个按钮直接变成**白底白字**，完全读不出来。
  `_button` 的 6 个 variant / `_pill` / chips / 倒计时遮罩全部要跟着换。
* **近处边线加强不能各算一套参数**。原来 y 用 `botY - stageH*0.42` 反推 t≈0.42，
  half 却取 `lerp(...,0.58)`，这段亮线整体偏离边线，在跑道外面拉出一条游离的斜杠。
  正解：走**同一条边线**的端点，只让颜色沿 y 分段。
* **判定后的音符要快速淡出**。原来 700ms，音符滑过踏板旁边还很亮，抢判定台的戏；
  改 380ms，漏接上限 0.35。
* **漏接不使用粉红/红色**（康复红线）：`VERDICT_STYLE.miss` 改 `#96A5B4` 冷灰，
  文字用两层冷灰光晕，读起来是「过去了」而不是「出错了」。

### 19.7 测试

`rhythm-headless-test` 133 项全绿。其中两条断言随本次改动更新：

* 对局底栏从四个胶囊收成两个圆形图标（暂停 / 退出），
  音量与节拍移进暂停面板 —— 断言改成 **play 里没有 vol/beat，pause 面板里必须有**。
* `VERDICT_INK` 注释从「白底专用」翻转为「暗底专用」，颜色取 `VERDICT_STYLE` 那套浅色。

## 20. 门控模式：接到才出下一个（2026-11-01 定版）

用户原话：

> 不需要根据音乐节奏了，现在音符一下子来一堆一下子半天不来，有问题，
> 我需要接到音符才会出现后面的音符，确保接到全部音符，不存在漏接，
> 让康复患者可以训练自己，还有背景可不可以设置 3 个，可以自己选。

### 20.1 「一堆 / 半天不来」的数学来源

旧模型是**时间表驱动**：`buildChart()` 预先算出每个音符的绝对时刻（`t += gapMs`），
引擎按时间把它们一个个放到场上，过了窗口就记 MISS。

后果是——**下一个音符什么时候来，跟患者有没有接到完全无关**：

- 屏上同时挂着的音符数 ≈ `approachMs / noteGapMs`。标准档 3400/1450 = **2.3 个**，
  挑战档 2800/900 = **3.1 个**。这就是「一下子来一堆」。
- `restRate` 每 N 个音符把间隔拉长到 1.5 倍（1450 → 2175ms），加上漏接后连击断、
  屏上一清，就是「半天不来」。
- 两个症状是**同一个结构的两端**：节奏由表决定，患者只是被动追。

所以用户要的「接到才出下一个」不是加个开关，是**换驱动源**：从「时间表」换成「患者」。

### 20.2 换驱动源要付的代价（必须先认下来）

> **一旦音符由命中触发，「准时」这个概念就消失了。**

患者永远不会迟到、也永远不会早到——没有外部节拍可对。旧的三档判定靠
`deltaMs`（相对 `targetTimeMs` 的偏差）分级，`miss` 靠窗口关闭产生，
这两件事在新模型里**物理上都不存在**。所以整条判定链必须重写，不是微调。

### 20.3 新的音符生命周期

```
approaching ──到达判定线──→ waiting ──方向对且稳住 stableMs──→ holding
     ↑                          │                                 │
     │                    （一直等，不惩罚）              ──保持 holdMs──→ done
     └──────────────────────────┴──── 中途离开正确一侧（记一次 flap）──┘
```

- 场上**永远只有一个**音符；它飞到判定线就**停在那里等**，不会冲过去。
- 完成之后才进入「喘息 `gapMs`」→「生成下一个」→「飞 `approachMs`」。
- 因此**不存在漏接**：音符不会自己溜走。

### 20.4 判定只看「稳不稳」

分级依据是**抖动次数 `flaps`**：进入正确一侧并稳住之后，中途离开过几次。

| flaps | 判定 | 文案 |
|---|---|---|
| 0 | PERFECT | 稳住了 |
| 1–2 | GREAT | 很稳 |
| ≥3 | GOOD | 完成了 |

时间只**记录**（`reactionMs` 到位用时 / `heldMs` 保持时长），**不参与评分**。

理由：平衡功能训练里「快」是危险信号——抢动作、身体冲过头、重心来不及回收，
都是跌倒的典型路径。这条口径比旧版「越快越准越高分」更贴康复目标。

### 20.5 卡住怎么办：一直等 + 提示逐级加强

门控下最怕的不是漏接，是**卡死**——患者做了但游戏没反应，会以为坏了。

| 等待 | 提示 | 做法 |
|---|---|---|
| 3 秒 | 第 1 级 | 音符放大、外晕变亮（纯视觉，不说一个字） |
| 6 秒 | 第 2 级 | 该去的那块判定台点亮并呼吸 |
| 10 秒 | 第 3 级 | 语音「往左一点 / 往右一点 / 回到中间」 |

**永不自动放行**。超时自动跳过等于把「没接到」偷偷变成「接到了」，
训练就失去意义（用户明确否掉了这一项）。

### 20.6 评测口径整组替换

旧版三个「准确率」在门控下有两个数学上恒等于 100%（方向不对就完不成，
完成数就是分母），继续显示等于骗人：

| 旧 | 新 | 说明 |
|---|---|---|
| 节奏准确率 | **稳定度** `stabilityRate` | (完美×1 + 很稳×0.75 + 完成×0.4) / 完成数 |
| 方向准确率 | **左右均衡** `balanceRate` | 1 − \|左−右\| / (左+右)，只做一侧时 = 0 |
| 综合命中率 | **平均节奏** `paceSec` | 实际用时 / 完成数 |

「平均到位用时」`avgReactionMs` 也留着，但**只记录不打分**——治疗师要看反应速度，
患者不该为它焦虑。

评级 `_grade()` **只看稳定度**，不看完成数量：完成数由患者速度决定，
拿它评级等于鼓励抢动作。

`judgeVersion` 升到 **`v3`**。**v3 与 v1/v2 的命中率不可直接对比**
（v1/v2 是「按时间表放音符，接不住就 MISS」，v3 是「接到才放下一个，没有 MISS」）。

### 20.7 参数体系：删了什么、加了什么

删除（它们描述的都是「机器按时间表放音符」）：

- `perfectMs` / `greatMs` / `goodMs` / `earlyFactor` —— 时间窗口，没有时间可对
- `noteGapMs` —— 音符间隔，改由患者速度决定
- `restRate` —— 呼吸间隔，机器不再插空
- `snapToBeat` / `noteStepBeats` / `prepBeats` —— 吸附拍点，音乐已不承担节奏
- `sameSideGapMs` / `comboBreakOnMiss` —— 针对漏接的后门，已无漏接
- `beatClickOn` —— 拍点点击音，没有拍点了

新增：

- **`gapMs` 音符喘息**：完成一个之后隔多久出下一个
- **`holdMs` 保持要求**：稳住之后还要保持多久才算完成 ← 新难度的核心
- **`backgroundId`**：三套背景
- **`melodyOn`**：命中推进旋律

`approachMs` 的含义也变了：它**不再承担预判难度**（音符到线会停住等，来不及也没关系），
只决定视觉节奏感。所以可以从 3400ms 压到 1300~2200ms —— 一局 90 秒才有 30~45 个的量。

### 20.8 五档预设的新含义

难度由三件事一起决定：`gapMs`（喘息，越小越赶）+ `approachMs`（飞行，越短越不容易看清）
+ `holdMs`（保持，越大越考验稳得住）。

| 档 | gapMs | approachMs | holdMs | 周期 | 90 秒约 |
|---|---|---|---|---|---|
| 1 入门 | 400 | 2200 | 240 | 2840ms | 21 个（60 秒） |
| 2 轻量 | 340 | 2000 | 300 | 2640ms | 28 个（75 秒） |
| 3 标准 | 250 | 1700 | 400 | 2350ms | 38 个 |
| 4 进阶 | 170 | 1500 | 480 | 2150ms | 49 个（105 秒） |
| 5 挑战 | 100 | 1300 | 560 | 1960ms | 61 个（120 秒） |

旧时间表模式同档位是 62 个，但那个数字是「必须接住才有的量」，一旦漏几个就崩；
门控下这 38 个是真的一个一个做完的。

### 20.9 音乐：命中推进旋律

门控下音符是患者自己「叫出来」的，音乐不该是旁边放着的一首曲子，
而是**他每完成一个动作就往前走一步的旋律**。停下来，音乐就悬在那儿等他。

实现取巧：**只存一个 C5 钟琴音**（`tools/gen_rhythm_tones.py` 合成，39.7KB wav），
播放时改 `playbackRate` 变调：

```
C5 1.000 / D5 1.125 / E5 1.250 / G5 1.500 / A5 1.667 / C6 2.000
```

微信 `InnerAudioContext.playbackRate` 支持 0.5~2.0，正好一个八度。变调同时改变时长，
但钟琴本来高音余音就短，听起来反而更自然。省掉 5 份素材与 5 次解码。

六个 `InnerAudioContext` 按度数各一个（不复用同一个）：同一对象在余音未消时再次
`play` 会硬切，快速连击听起来像卡带。

旋律走向是固定的 12 步循环（`MELODY`），**不用 `Math.random`**——同一个患者每次练
同一首，旋律完全相同，才谈得上「练熟」。

音色（原「曲目」）改成**调式与音色的选择**：BPM 不再参与任何计算。
三首 m4a 只在 `melodyOn` 关闭时作为循环背景乐用。

### 20.10 三套背景：同一套几何，只换光与色

`theme.js` 里 `dawn` / `dusk` / `moon` 三套，字段完全对应：

- 地平线位置、山形、跑道透视、判定线**全部一样**；
- 只有天空渐层、光源（位置/大小/颜色）、远山色温、地面渐层、地平线光色在变；
- `dusk` 额外有**远城灯火**（画在远山之前，被剪影吃掉一半）；
- `moon` 额外有**星点**（确定性 hash，越靠地平线越稀 = 大气消光）与**冷银地平线**。

为什么不做三张不同的画：

1. 美术成本——换元素要重画跑道两边的所有东西，工作量是换色的三倍；
2. **患者不迷路**——康复训练里最怕「界面一变就不会用了」，背景只是心情，
   操作语言必须稳定；
3. 三套都是暗调，理由只有一个：**高明度底色撑不起辉光**（糖果色那版的教训）。

**车道色温（左冷青 / 中暖白 / 右琥珀）三套完全一致，永远不改**，有测试守着
（`[9] 三套背景的车道色温完全一致`）。那是功能语义，不是装饰。

入口：开始页右上角三枚色卡（患者自己点，`cfg.set('backgroundId')` 记住）。
不放卡片里是因为卡片高度按内容贴底算，多一行会把「玩法三步」和「本局参数」挤掉。

### 20.11 已知代价（必须让治疗师看见）

**只做一侧的患者会彻底卡住。**

严格交替的序列下，一个只会往左偏的患者完成第一个左侧音符之后，
会永远卡在第一个右侧音符上 —— 90 秒一局只完成 1 个。

这是「不自动放行」的直接后果，也是**真实的训练信息**：单侧代偿比「分低」严重得多。
`balanceRate = 0` 会把它直接摆到结算页上。治疗师的处置是：降难度、检查「左右反向」、
或在旁边给口令。

测试 `[5]` 钉住了这个行为，免得以后有人为了「好看」偷偷改成超时放行。

### 20.12 踩到的坑

| 现象 | 真因 | 修法 |
|---|---|---|
| **音符停在判定线上却看不见** | 绘制顺序是「音符 → 判定台」。时间表时代音符嗖地穿过去看不出来，门控之后它**停在台面正中**，被整块盖住 | 改成「判定台 → 音符 → 玩家」：判定台在地面上，音符浮在它上面 |
| 结算页出现 `2.7e-8 秒` | 喘息时间用「命中时刻」算，但那一帧 `nextSpawnAt` 已经被下一帧覆盖 | 测试改成在**命中那一帧**读 `nextSpawnAt - judgedAt` |
| 逐级提示在暂停时还在涨 | `waitMs` 由 `now - targetTimeMs` 算，暂停时 `now` 冻结所以其实不涨 | 测试补了一条断言守着 |
| 开始页标题还写「选择曲目」 | 曲目语义已经变成「音色」 | 改成「选择音色」，副标题去掉 BPM |
| 三套背景车道色温被我写成三套 | 觉得「配色不同才好看」，违反了自己刚写的约束 | 三套统一，加测试 |
